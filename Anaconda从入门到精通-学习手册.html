第 1 章初识 Anaconda：生态、定位与为什么学它

1.1 正式定义

概念定义

Anaconda 是一个面向数据科学与科学计算的 Python/R 发行版（Distribution）与工具集合，核心由三部分构成：

1）conda——跨平台、跨语言的包管理器与环境管理器（这是你 90% 时间打交道的部分）；
2）一个预装了 800+ 科学计算包（NumPy、pandas、SciPy、Matplotlib、Jupyter、scikit-learn 等）的发行版本体；
3）Anaconda Navigator 等 GUI 工具与云端仓库（repo.anaconda.com / anaconda.org）。

大白话与类比

把写代码想象成做菜。Python 是厨房，包（package）是食材和锅具。直接用 pip 装包，相当于把所有食材一股脑倒进一口大锅里——做个番茄炒蛋要桂皮，做咖喱又要香草，时间一长锅里什么都混在一起（这叫“依赖地狱”，典型症状就是 ModuleNotFoundError 和版本冲突）。

Anaconda/conda 给你的方案是“分格餐盘”：每道菜（每个项目）一个独立格子（环境），番茄炒蛋的格子里只有番茄和鸡蛋，互不串味；想换食材，整格端走重建，不影响别的格子。而 conda 这个“管家”还负责采购（从不同的超市=频道，下载连皮带骨、开箱即用的预制食材），甚至锅具本身（Python 解释器）也可以每格各配一口——A 格用铁锅（Python 3.10），B 格用不粘锅（Python 3.13）。

初学者最容易被一堆相近名词绕晕：Anaconda、Miniconda、conda、Miniforge、conda-forge、Anaconda Navigator、Mamba。下面这张生态地图请务必先看懂，后面所有章节都建立在它之上。

1.3 为什么要学：conda 解决的四个真痛点

  1. 依赖地狱：A 项目要 numpy<2，B 项目要 numpy≥2，装在同一个全局环境必然打架。conda 的环境让它们分家共处。
  2. 多 Python 版本并存：系统 Python 只能装一个，conda 可以按环境各配各的（3.9/3.11/3.13 同时在机器上）。
  3. 非 Python 依赖的编译地狱：pip install scipy 在无编译器的机器上装 C 扩展包可能当场失败；conda 包是预编译二进制，含 C/C++/Fortran 依赖一并装好——甚至能装 CUDA 工具链、R 语言、gcc 编译器这类“非 Python 食材”。
  4. 可复现性：一条 environment.yml 就能把环境在同事的电脑上原样重建，告别“在我机器上能跑”。

1.4 第一个五分钟实验

安装完成后（安装见第 2 章），打开终端（Windows 用「Anaconda Prompt」或开始菜单里的 Anaconda 终端；macOS/Linux 用任意终端），依次执行：

bash 
# 查看工具本身版本——以后提问报错，别人第一句都会问这个
conda --version
# 看看机器上现在有哪些环境（刚装完一般只有 base）
conda env list
# 看当前 conda 的整体状态：版本、路径、频道配置
conda info
conda 26.7.1          ← 版本号随安装时间不同而不同

# conda environments:
#
base  *  C:\Users\you\anaconda3        ← 星号表示当前所在环境
常见误区

误区：「Anaconda 和 Python 二选一」。错。Anaconda 里的 Python 就是标准 CPython，只是由 conda 打包分发。装了 Anaconda 的机器完全可以再有系统 Python / Microsoft Store Python，互不冲突——关键是搞清楚终端里当前用的是哪一个（见 5.5 节 which python）。

误区：「装了 Anaconda 就不用学命令行」。Navigator 图形界面能覆盖 30% 的日常操作，但环境导出、离线部署、排错、CI 里全都离不开命令行。本手册以命令行为主，Navigator 专节见 12.4。

本章小结
  • Anaconda = conda（管家）+ 发行版（全家桶）+ 仓库生态（超市）；学 Anaconda 本质上是学 conda。
  • 三个安装器：全家桶选 Anaconda；硬盘小、有洁癖、公司有许可顾虑选 Miniconda；想彻底只用免费 conda-forge 选 Miniforge。
  • conda 的四大价值：环境隔离、多 Python 并存、预编译二进制包、可复现。
  • 频道是“超市”，环境是“分格餐盘”，base 环境是管家自己家——别在 base 里大装特装。

第 2 章安装、更新与初始配置

2.1 正式定义：安装器选型

概念定义

安装器（Installer）是把你带入 conda 世界的第一个程序，它只做一件事：在磁盘上放好一个自包含的 base 环境（含 conda、一份 Python、激活脚本）。之后所有升级、装包、建环境都由 base 里的 conda 自己完成。

三类安装器：Anaconda Distribution（全家桶，约 1GB+，图形安装向导）、Miniconda（约 100MB，官方精简）、Miniforge（社区精简，默认频道 conda-forge）。

大白话与类比

选安装器就像装修入住：Anaconda 是“拎包入住”——冰箱彩电洗衣机全有，进来就能做数据分析；Miniconda 是“毛坯+管家”——房子空着，但管家已就位，要什么按需搬进来，硬盘占用小得多；Miniforge 是“毛坯+管家+只逛免费超市的会员卡”——从第一天起就只从 conda-forge 进货，省去后续改配置的麻烦（且完全规避 Anaconda 商业条款问题，见 17.3）。

给学习者的建议：个人学习机装 Anaconda 或 Miniconda 均可；若在公司环境（尤其 ≥200 人的企业）且无商业许可，优先 Miniforge。

2.2 Windows 安装（逐步）

  1. 到官网（repo.anaconda.com 或 anaconda.com/download）下载 Anaconda3-xxxx-Windows-x86_64.exe；Miniconda 同理选 Miniconda3-latest-Windows-x86_64.exe。
  2. 双击安装，关键勾选项逐条解释：
    安装向导选项建议原因
    Install for: All users / Just MeJust Me（仅自己）装到用户目录，无需管理员权限，后续升级/装包不遇权限墙
    安装路径无空格无中文的短路径，如 C:\Users\you\miniconda3老版本工具链对含空格/中文/OneDrive 同步目录的路径支持差，是玄学报错高发区
    Create shortcuts勾开始菜单出现「Anaconda Prompt」等入口
    Add to PATH（加入系统环境变量）官方建议不勾；新手建议不勾勾上会与系统里已有的 Python 抢地盘，导致"终端里 python 不是我想的那个"。不勾时通过「Anaconda Prompt」专用入口进入，隔离最干净
    Register as default Python（设为系统默认）机器上没别的 Python 就勾；否则不勾勾上后 IDE/其他软件默认调用它
    Clear package cache upon completion勾省几 GB 磁盘
  3. 完成后从开始菜单打开 「Anaconda Prompt (anaconda3)」（Miniconda 用户为对应 Prompt）。你会看到提示符前多了 (base)——这就是激活标记。
常见误区

误区：装完在 cmd / PowerShell 里敲 conda 提示“不是内部或外部命令”。这不是坏了——你没勾 PATH 时本来就不认识。两个解法：①以后都用「Anaconda Prompt」；②执行一次 conda init cmd.exe 或 conda init powershell（把激活逻辑写进终端启动脚本，之后任意终端可用）。

Windows 专属坑：PowerShell 报「在此系统上禁止运行脚本」。首次在 PowerShell 用 conda 需要放开执行策略：Set-ExecutionPolicy -Scope CurrentUser RemoteSigned，选择 Y。（若公司策略禁止，改用 Anaconda Prompt 即可。）

2.3 macOS 安装

  • 看准芯片架构：Apple Silicon（M 系列芯片）下载 MacOSX-arm64 版；Intel 老机型下载 x86_64。下错了会在 Rosetta 转译层里跑，性能打折且包兼容性差。终端里 uname -m 返回 arm64 即 Apple Silicon，x86_64 即 Intel。
  • 两种形式：.pkg 图形安装（全鼠标点选），或 .sh 脚本安装（终端执行，适合远程/自动化）：
bash · macOS/Linux 通用 
# 脚本式安装（macOS / Linux 通用范式，路径换成你下载的文件）
bash Miniconda3-latest-MacOSX-arm64.sh -b -p ~/miniconda3
#   -b  批处理模式：不问问题，全默认
#   -p  指定安装目录（prefix）
# 之后让终端"认识"conda：把初始化写进 ~/.zshrc（新版 macOS 默认 zsh）
~/miniconda3/bin/conda init zsh
# 重开终端，或手动让配置生效
source ~/.zshrc
(base) you@Mac ~ % conda --version
conda 26.7.1

2.4 Linux 安装（含静默部署/服务器场景）

bash 
# 1) 下载（版本号以官网最新为准；此为示例文件名）
wget https://repo.anaconda.com/miniconda/Miniconda3-latest-Linux-x86_64.sh
# 服务器没有 wget 时可用 curl：
curl -O https://repo.anaconda.com/miniconda/Miniconda3-latest-Linux-x86_64.sh
# 2) 校验完整性（可选但推荐：对比官网公布的 SHA256）
sha256sum Miniconda3-latest-Linux-x86_64.sh
# 3) 安装到用户目录（不碰系统 Python，无需 sudo）
bash Miniconda3-latest-Linux-x86_64.sh -b -p $HOME/miniconda3
# 4) 初始化默认 shell（Linux 常见 bash；服务器上可只对当前会话激活）
$HOME/miniconda3/bin/conda init bash
# 或临时激活（不写配置，适合跳板机/容器）：
source $HOME/miniconda3/bin/activate
常见误区

误区：Linux 上用 sudo 安装到 /opt 更“规范”。后果：所有 conda 操作都需要 root，且多用户共用一个 pkgs 缓存互相覆盖。正确姿势是每用户装自己的 miniconda 到家目录；确需共享时见第 14 章内网部署。

误区：装完不重开终端就敲 conda。conda init 修改的是 shell 启动脚本，必须新开一个终端（或 source ~/.bashrc）才生效。

2.5 首次配置：把频道改成国内镜像（网络慢的救星）

conda 默认从 repo.anaconda.com（境外）下载，国内直连常年在几十 KB/s 徘徊。清华大学 TUNA 等镜像站同步了官方仓库与 conda-forge。配置只是往 ~/.condarc（Windows 为 C:\Users\你\.condarc）写几个 URL：

bash · 推荐做法（命令式，写进配置） 
# 用 conda config 增/删频道（等价于手改 .condarc，但不会写错格式）
conda config --remove-key channels        # 先清掉旧频道设置（若报"key not exist"属正常）
conda config --add channels https://mirrors.tuna.tsinghua.edu.cn/anaconda/pkgs/main/
conda config --add channels https://mirrors.tuna.tsinghua.edu.cn/anaconda/pkgs/r/
# conda-forge 镜像（社区频道，建议常备）
conda config --add channels https://mirrors.tuna.tsinghua.edu.cn/anaconda/cloud/conda-forge/
# 关闭默认频道的自动追加，并显示频道来源，便于排查"包从哪来"
conda config --set show_channel_urls true
# 查看最终生效配置
conda config --show-sources
==> /home/you/.condarc <==
channels:
  - https://mirrors.tuna.tsinghua.edu.cn/anaconda/cloud/conda-forge/
  - https://mirrors.tuna.tsinghua.edu.cn/anaconda/pkgs/r/
  - https://mirrors.tuna.tsinghua.edu.cn/anaconda/pkgs/main/
show_channel_urls: True
注意频道顺序的“反直觉”：--add 是往列表前面插，所以后 add 的优先级更高。上面示例最终优先级：conda-forge > r > main。频道优先级的完整规则与坑见第 7 章。镜像 URL 会随镜像站迁移而调整，配置前请核对 TUNA 帮助页的最新地址（待核实——镜像地址存在变更可能）。

2.6 更新与卸载

bash 
# 更新 conda 自身。26.5 及以后推荐新命令：
conda self-update
# 老版本（<26.5）用经典命令（在 base 环境执行）：
conda update -n base conda
# 更新 Anaconda 发行版的整套包（仅 Anaconda 全家桶用户有意义）：
conda update -n base --all
# ---- 卸载 ----
# Windows：开始菜单「Uninstall-Anaconda/Miniconda」，或 控制面板→程序
# macOS / Linux：安装目录是自包含的，整个删掉即干净卸载（-rf 前请三思路径！）
#   rm -rf ~/miniconda3
# 再清理两个残留：~/.condarc（配置）与 ~/.conda / ~/.condarc 尾部 conda init 注入的 shell 片段
#   conda init --reverse   # 先用官方命令还原 shell 初始化，再删目录更稳妥
常见误区

误区：一装好就 conda update --all 把 base 全升到最新。base 环境里的包是 conda 自身运行的基石，全家桶整体升级可能引入不兼容；base 只升 conda 相关组件，业务包装到独立环境——这是官方反复强调的最佳实践。

第 3 章核心概念与工作原理：包、环境、频道、求解器

本章是全书的理论地基。把这一章读懂，后面十几章的每一条命令你都能“知其所以然”，排错时也不再是抓瞎。

3.1 正式定义：四个核心概念

概念定义

包（Package）：一个自包含的压缩归档（新格式 .conda，旧格式 .tar.bz2），内含：文件本体（site-packages/ 下的模块、可执行程序）、入口脚本、激活/反激活钩子脚本，以及一份描述“我叫什么、版本、依赖谁”的元数据（info/index.json）。

环境（Environment，术语“前缀 prefix”）：磁盘上一个完整独立的目录树，含一份独立的 Python 解释器、独立的库集合、独立的命令行入口。环境之间零文件共享——这是比传统 virtualenv（软链接共享）更彻底的隔离。

频道（Channel）：包的托管位置（URL 或本地路径）。conda 按频道优先级从多个频道寻找满足需求的包。

求解器（Solver）：把“你想要的包”+“已有环境”+“各频道里所有可用版本”三组约束输入，计算出唯一一套互不冲突的安装方案（SAT 满足性求解）的组件。当前默认为 conda-rattler-solver（conda 26.10 起；此前默认 libmamba）。

大白话与类比

包=“带说明书与安装图的整箱家具”，箱上贴着三联标签 名称-版本-构建号（如 numpy-2.1.0-py312h…_0，构建号 _0 是“同一版本的第几次重新打包”——同版本不同构建可能换了底层库，区别可大可小）。环境=一间已摆好家具、可拎包入住的独立房间；频道=品牌仓库；求解器=装修设计师：你提需求（“要一张桌子还得配得上门厅已有的柜子”），它在成千上万种组合里算出既满足你、又不打架的唯一方案。

3.3 环境的物理形态：目录树与隔离原理

“环境”不是抽象概念，就是磁盘上一棵真实目录树。以 Linux/macOS 为例（Windows 把 bin 换成 Scripts、lib/python3.x 换成 Lib 即可）：

目录树

│   └── python                 ← 这是"这个环境专属的"解释器可执行文件
├── lib/python3.12/site-packages/   ← 该环境的所有第三方包，只属于它
├── conda-meta/                ← 环境的"账本"：每个已装包的 json 记录

│   └── python-3.12.x-h….json

│   └── numpy-2.1.0-py312h…/  ← 其他环境装同款包时从这里硬链接过去

3.4 求解器：从需求到方案的 SAT 之旅

公式与推导思路

把依赖求解形式化。设候选包集合 P（各频道所有版本×构建号），每个包 p 有依赖约束集 D(p)（如 numpy ≥2.1, <3）。求解目标即找子集 S ⊆ P 使：

① 需求满足：用户指定包 ∈ S（或已有环境保留包 ∈ S）；
② 依赖闭包：∀p∈S, D(p) 在 S 中可满足；
③ 互斥约束：同名包在 S 中至多一个 (名称, 版本, 构建) 组合；
④ 目标函数：在满足①–③的方案中选“版本尽量新、改动尽量小、优先高优先级频道”的解。

这是一个 NP-hard 的 SAT（布尔可满足性）问题——这就是约束越多、环境越大、频道越多，Solving environment… 转得越久的理论原因。经典求解器逐条回溯搜索；libmamba/rattler 借用 C++/Rust 实现的数据库索引与预处理，把常见情况从“分钟级”压到“秒级”。

大白话

liken 到相亲匹配软件：你的条件（要 Python 3.12、要 TensorFlow 2.16、老环境里已有某版 protobuf）是“征婚要求”；每个候选对象（包版本）都自带一堆要求（“我必须配 1.x 的 protobuf”）。求解器必须找到一桌人——既有你要的主宾，每人带来的朋友之间还都不打架。桌越大人越多，匹配越慢。

常见误区

误区：“求解器慢 = 网络慢”。两码事。转圈圈的 Solving environment… 是本地 CPU 计算；下载慢才是网络问题（表现为进度条卡 0%）。对症下药：前者靠 15 章的求解优化，后者靠 2.5 节的镜像。

3.5 包的三段式命名与版本匹配语法速览

写法含义示例
name=version=build完全锁定：版本与构建号都指定conda install python=3.12.1=hxxxx_0
name=version锁版本（接受任意构建号）python=3.12 会装该大版本下最新
name=主.次.*通配版本段：匹配 3.12.*（3.12.x 任意 x）conda install python=3.12.*
"name=ver [约束]"区间约束（引号防 shell 吞符号）"numpy>=2.1,<3"
channel::name强制从指定频道取该包conda install conda-forge::numpy

  • 四概念闭环：包（带依赖说明的家具箱）→ 环境（独立房间+独立解释器）→ 频道（仓库）→ 求解器（设计师，SAT 问题）。
  • 安装六步流水线：repodata → 求解 → 事务 → 下载 → 解包硬链接 → 收尾钩子；慢的大头是第 2 步。
  • 环境=自包含目录树，conda-meta 是账本；不能直接拷贝/移动。
  • 包标识三段式 名称-版本-构建号；版本语法 =、.*、区间、channel::pkg。

第 4 章conda 命令体系与基础操作

4.1 正式定义

概念定义

conda CLI 采用「主语 + 动词 + 修饰」的三段语法：conda <子命令> [对象] [选项]。子命令分四大族：

环境族：env（list/create/export/remove…，多数可省 env 直写 create）；
包族：install / update / remove / list / search；
配置族：config / info；
运维族：clean / doctor / run / init / self-update。

两个全局修饰符贯穿所有命令：-n 环境名（对哪个环境动手）与 -y（跳过确认，脚本/CI 必备）。

大白话

像点外卖的话术：“conda（叫管家）install（上货）numpy（这个货）-n ml（放到 ml 那个房间）-y（别再问我确认）”。不给 -n 就默认装到“当前激活的环境”——忘了这条，装错房间的事故占比极高。

第 5 章环境管理详解：从建立到消亡的完整生命周期

5.1 正式定义

概念定义

conda 环境管理指对"独立前缀目录"全生命周期的操作集合：创建（create）、激活/退出（activate/deactivate）、改名（rename）、克隆（clone）、导出/导入（export/create -f）、按修订回滚（--revision）与删除（env remove）。环境有两种命名方式：

命名环境（-n）：存放在 <安装根>/envs/<名字>，用名字引用；路径环境（-p/--prefix）：任意目录，用全路径引用，适合多项目分盘管理。

大白话

命名环境像“公寓 501 室”，说房间号就找得到；路径环境像“自建别墅”，你得报完整地址。两者能力一致，日常用名字最省心；服务器上把环境建在项目盘 /data/envs/xxx 用 -p，方便和项目数据放一起备份。

5.2 激活的本质：到底改了什么

原理

conda activate 不是“打开一个新窗口”，而是在当前 shell 进程里做环境手术：把该环境的 bin（Windows 为 Scripts + \Library\bin）插到 PATH 最前；设置 CONDA_PREFIX、CONDA_DEFAULT_ENV 等变量；执行环境的 activate.d/*.sh|*.bat|*.ps1 钩子（包可借此设 CUDA_HOME、LD_LIBRARY_PATH 等私有变量）。deactivate 则逆序还原。所以“哪个 python 生效”= PATH 里排最前的那个。

第 6 章包管理详解：安装、锁定、升级与卸载

6.1 正式定义

概念定义

conda 的包管理围绕四个动作与三层信息展开。动作：search（查）、install（装）、update（升）、remove（卸）。信息三层：规格（spec，你要什么）→ 求解（求解器算出的方案，即 transaction） → 账本（conda-meta 里落账的 installed 记录）。命令行里你只写第一层，后两层由 conda 维护。

大白话

第 7 章频道机制与 .condarc 配置精讲

7.1 正式定义

概念定义

频道（Channel）是包的托管仓库 URL（或本地目录）。conda 在解决依赖时按 .condarc 中的 channels 列表顺序自上而下赋予优先级（列表第一行优先级最高）。.condarc 是 conda 的 YAML 格式用户级/系统级配置文件，控制频道、镜像、求解器、并发、安全策略等几十项行为。

三种引用频道的粒度：全局（写进 .condarc 的 channels）；单次命令（-c 频道 或 --override-channels）；单包（频道::包名 三明治语法）。

大白话与类比

频道=采购超市列表，列表顺序就是“偏好顺序”。condarc 是这张购物偏好卡：先逛哪家超市（channels）、遇到断货怎么办（channel_priority）、认不认代购（channel_alias 镜像）。conda-forge::numpy 这种写法则是点名“这袋盐必须去某家买”。

7.2 频道优先级：strict 模式的规则与代价

规则（channel_priority: strict，conda 4.7+ 的默认与官方推荐）

求解器先在优先级最高的频道内找齐一套自洽方案，找不到才降级到下一频道。同频道内才比较版本新旧。代价：高优先级频道哪怕版本更旧也会被采用——这正是“为什么装出来是旧版”的多数答案。

对照的 flexible（旧默认）模式：所有频道混在一起比版本新旧，可能“同一环境的包一半来自 A 频道一半来自 B 频道”，出现双 BLAS（MKL 与 OpenBLAS 并存）之类的深层冲突——当年无数 import numpy 崩溃事故的元凶。4.7 时代改为默认 strict 就是为了治这个。

常见误区

误区：“我明明没加 -c，为什么包装出来是旧版？”检查两点：① channels 列表顺序（conda config --show channels），第一位的频道版本旧则它说了算；② 你的 spec 写的是 numpy 裸名——裸名=“这版也行”。想要新版，写 numpy=2.3 或把高版本所在频道调到优先级1。

致命误区：混用 defaults 与 conda-forge 且用 flexible。典型症状：numpy 同时出现 MKL 与 OpenBLAS 变体、import 时段错误/性能骤降。团队实践共识——一个环境只用一个主频道（要么全 defaults，要么全 conda-forge），需要个别包时用 频道::包名 点名引入而不是全局加频道。

第 8 章conda 与 pip：关系、区别与正确混用

8.1 正式定义

概念定义

pip 是 Python 官方的包管理器，只管 PyPI 上的（几乎全是）Python 包；conda 管任何语言的二进制包及其依赖树，并额外承担环境管理。pip 不是 conda 的替代品，是它的“外挂货架”：PyPI 上 60 多万个包，conda 频道里只有其中一小部分——剩余的只能 pip 装。

两者可以共存于同一个 conda 环境（conda 装的 Python 里自带 pip），但必须遵守固定纪律（见 8.3）。

大白话与类比

conda 像大型商超：货架少而精（预编译、连锅带灶、甚至非 Python 的锅），品质稳定；pip 像万能淘宝：什么都买得到（纯 Python 的成品居多），但“安装现场要自己拼装”（源码编译）且不管你家厨房（环境）布局。最优策略：大件、带二进制依赖的、科学计算栈走商超；商超没的小玩意上淘宝补。

8.2 核心区别对照表

维度condapip
包来源conda 频道（defaults / conda-forge / 私有）PyPI（单一仓库）
包格式.conda / .tar.bz2（预编译，含非 Python 依赖）wheel（预编译）或 sdist（源码，需本机编译）
能装的东西Python、R、CUDA、gcc、MKL、FFmpeg、nodejs…仅 Python 包
环境管理原生（create/activate/导出/克隆）无（需配合 venv；且 venv 不能多 Python 小版本并存）
依赖求解SAT 求解器，会为整棵依赖树回退/协调版本逐包解析，遇到冲突常“硬装”，事后 import 才炸
改 Python 本身conda install python=3.11 可行不能（pip 装不了解释器）
典型弱项包覆盖面小；求解偶尔慢科学计算二进制包编译地狱；环境隔离靠外部

8.3 混用纪律（血泪教训结晶）

黄金规则

一个环境内：先用 conda 装出“骨架与重件”（Python、numpy、scipy、blas…），再用 pip 补“小件”；一旦用 pip 装过，就不要再回头用 conda 动同名/同依赖域的包。

原因机制：conda 的账本（conda-meta）看不见 pip 装的包（它们只记录在环境的 Lib/site-packages 与 pip 的记录里）。conda 后续求解时不知道 pip 已在某处装了 numpy 2.0，它按自己的计划再装一份 numpy 或删依赖，两份同名包在 site-packages 里互相覆盖——import 谁全看运气，出现“版本明明升级了还是旧的”“import 报莫名错误”等灵异现象。

bash · 正确姿势全流程 
conda create -n webapp python=3.12 -y
conda activate webapp
# ① 骨架交给 conda（能 conda 装的优先 conda）
conda install -y requests numpy
# ② conda 找不到 / 明确只有 PyPI 有的包，交给 pip
pip install some-pypi-only-pkg
# ③ 查账：两条命令各看各的
conda list                     # 会把 pip 装的包也列出来，但标 pypi 来源
pip list                       # 只看 pip 视角
# ④ 混装后“自检”：同名包是否被双份覆盖
python -c "import numpy; print(numpy.__file__, numpy.__version__)"
# ⑤ 事故现场清理（回滚到纯 conda 管理）：
pip uninstall 包名        # 先让 pip 卸干净它装的那份
conda install 包名         # 再由 conda 接管
# ⑥ 环境导出时的区别（重要！）：--from-history 只含你显式要求的包
conda env export --from-history -f env.yml    # 不含 pip 装的细节
conda env export -f env.yml                   # 完整快照（含 pip 小节）
# conda env export 的完整快照里，pip 包出现在独立小节：
name: webapp
channels: […]
dependencies:
  - python=3.12
  - numpy=2.1
  - requests=2.32
  - pip
  - pip:
      - some-pypi-only-pkg==1.4.2
常见误区

误区一：在 base 环境长期 pip install。base 的 Python 同时被 conda 自身使用，pip 乱装最易污染管理器自身。底线：base 不做开发环境。

误区二：conda 里装了 pip 包之后又跑 conda update --all。update 会按 conda 账本重排依赖树，与 pip 装的暗文件冲突。混装环境请冻结管理（spec 全带版本号，并参考 15 章求解优化）。

误区三：拿 python -m pip 之外的方式调 pip。裸敲 pip 可能命中别的环境的 pip（PATH 排最前者）。永远用 python -m pip install xxx——跟着当前 python 走，绝无歧义。

8.4 新趋势：conda 直接装 PyPI 包 conda ≥ 26.x（rattler 求解器）

26.x 起，conda 借助 rattler 求解器开始支持原生安装 PyPI 包（conda-pypi 能力）：在 conda 事务里把 PyPI 的 wheel 一并求解与安装，账本统一、避免“pip 暗装”。该特性较新，企业生产环境建议先行试点（特性状态待核实，以官方文档“Installing packages from PyPI with conda”章节为准）。传统混用纪律在过渡期内仍然适用。

图 8-1 conda 与 pip 各自记账、互不可见——混用纪律的底层原因

本章小结
  • 分工：conda 负环境+解释器+二进制重件；pip 负责 PyPI 独有小件。
  • 纪律：先 conda 后 pip；pip 装过就别再用 conda 动同域包；python -m pip 写法最保险。
  • 冲突原理是“账本盲区”；清理顺序：pip uninstall → conda install。
  • 导出环境用完整快照（含 pip 小节）才能跨机复现混装环境。

第 9 章工具横向对比：conda / venv / poetry / uv / Docker

9.1 正式定义与选型结论

概念定义

venv：Python 标准库自带的轻量虚拟环境（仅隔离 site-packages，不含解释器）。virtualenv：venv 的前辈，第三方实现。 poetry：面向“Python 应用发布”的依赖+打包+发布一体化工具。 uv：Astral 出品的新一代极速 pip/venv 替代（Rust 实现）。 Docker：操作系统级容器隔离（连系统库都隔离）。conda：跨语言二进制级包+环境管理器。

工具隔离层级装非 Python 依赖多 Python 版本速度最适场景
conda目录树级（含解释器）✅ 强项（MKL/CUDA/gcc/R）✅ 原生求解快慢看情况数据科学、科学计算、复杂二进制栈
venvsite-packages 级❌❌（跟随系统 Python）快纯 Python 小项目、零额外安装
virtualenv同 venv（功能更宽）❌❌快老 Python 版本下的 venv 替代
poetryvenv 层级❌❌中要发布到 PyPI 的库/应用、lock 严谨
uvvenv 层级（快得惊人）❌（但可下载管理 Python 本体）✅（uv python）极快现代纯 Python 项目、追求安装速度
DockerOS 级（连 glibc 都隔离）✅（镜像里啥都行）✅重部署交付、团队环境完全一致
大白话选型

一句话心智模型：conda 管“任何语言的食材”，venv 管“盘子的分格”，poetry 管“菜谱的出版”，uv 是“提速版 venv+pip”，Docker 是“整厨房连房子一起搬”。现实项目里它们经常组合：conda 环境 + Docker 容器 + （可选）容器内再用 venv——层级不冲突，职责不同。

第 11 章Jupyter Notebook / Lab 与多环境内核管理

11.1 正式定义

概念定义

Jupyter 内核（kernel）是 Notebook 背后真正执行代码的 Python 进程，由一份 kernel spec（~/.local/share/jupyter/kernels/…/kernel.json，Windows 在 %APPDATA%\jupyter\kernels\）描述：“用哪个解释器、带什么环境变量”。切换内核≠切换文件，而是切换执行环境。conda 环境安装 ipykernel 后即可注册为可选内核。

大白话

Notebook 是“操作面板”，内核是“流水线工人”。面板只有一个，工人可以随时换班——conda 的每个环境训练一名工人（装 ipykernel 并注册），面板右上角“换班按钮”（内核选择器）里就会出现他们。你 Notebook 里 import 的包，永远是当前当班工人（内核）带来的。

11.2 标准动作：给每个环境注册内核

bash 
# 内核装在哪个环境，哪个环境就能被 Notebook 选到：
conda activate ds
conda install -y ipykernel
# 注册：让所有 Jupyter 面板都能选到 ds（--display-name 是面板上显示的名字）
python -m ipykernel install --user --name ds --display-name "Python (ds 数据栈)"
# 再训练第二名工人：
conda activate dl-torch
conda install -y ipykernel
python -m ipykernel install --user --name dl-torch --display-name "Python (dl GPU)"
# 查看现有内核清单 / 删除注册（删的只是“排班表条目”，环境本身不动）：
jupyter kernelspec list
jupyter kernelspec uninstall ds
Available kernels:
  python3        /home/you/.local/share/jupyter/kernels/python3
  dl-torch       /home/you/.local/share/jupyter/kernels/dl-torch
  ds             /home/you/.local/share/jupyter/kernels/ds
常见误区

误区：“我在 ds 环境装的包，Notebook 里 import 报错”。先看 Notebook 右上角内核是不是 ds——多数时候它还停在 python3（base 的默认内核）。在 Notebook 里执行 import sys; print(sys.executable) 可一眼验明正身。

误区：nb_conda 装了就万事大吉。老牌方案 conda install nb_conda（装在运行 Jupyter 的那个环境）可自动发现所有 conda 内核，但历史兼容问题不少；手动 ipykernel 注册（上文标准动作）最稳、可控，是社区主流做法。

第 13 章环境分享与复现：yml、锁文件与 conda-pack

13.1 正式定义

概念定义

环境复现的三层工具：environment.yml（conda 官方的人类可读描述：名字+频道+依赖清单）；锁文件（conda-lock 等：每平台每包锁定“版本+构建+下载地址+哈希”，最严格）；conda-pack（把已装好的环境整个打成 tar 包，解包即用，适合离线/同构机器搬运）。

大白话

yml=“菜谱”（对方按菜谱自己买菜做饭，结果基本一致但酱油牌子可能略不同）；锁文件=“中央厨房预制盒”（连食盐克数都锁死）；conda-pack=“把做好的整桌菜原样端走”（要求对方锅灶型号和你一样=操作系统与架构相同）。

13.2 environment.yml 的生成与消费

bash 
conda activate ds
# A. 完整快照：环境当前真身的每一件（含间接依赖、含 pip 小节）——适合“原样重建”
conda env export -f environment.yml
# B. 精简清单：只记你显式要求过的包（--from-history）——适合“配方分享/长期维护”
conda env export --from-history -f environment.yml
# C. 跨平台分享推荐：不锁构建号、不带 platform 杂项
conda env export --no-builds -f environment.yml
# 消费端（对方机器）：
conda env create -f environment.yml             # 名字用文件里的 name
conda env create -f environment.yml -n 新名字   # 或改名落地
# 后续增量更新（文件改了想让环境跟上）：
conda env update -f environment.yml --prune
yaml · 一份讲解版 environment.yml 
name: ds                    # conda env create 时默认采用的环境名
channels:                   # 顺序即优先级——复现的关键！漏写=对方装出不同版本
  - conda-forge
  - defaults
dependencies:               # 主清单：conda 包（版本号可选）
  - python=3.12
  - numpy=2.1
  - pandas
  - matplotlib
  - pip                     # 声明“下面有个 pip 小节”
  - pip:                    # PyPI 独有包写这里（第8章的混装记忆点）
      - some-pypi-only-pkg==1.4.2
variables:                  # 环境级环境变量（较新 conda 支持）
  PROJECT_ROOT: /data/proj
常见误区

误区：export 出的完整快照丢给 Windows 同事却装不上。完整快照常含 libgomp 等 Linux 专属包与构建号锁。跨平台分享用 --no-builds 或 --from-history；同平台机群（公司全是同一 OS）才用完整快照。

误区：yml 里忘写 channels。对方默认频道顺序与你不同，求解结果悄然不同——“明明同一个文件装出来不一样”的头号原因。

13.3 conda-lock：逐哈希复现（CI/生产级）

bash 
# conda-lock 是社区标准锁定工具（需先 conda install -c conda-forge conda-lock）
conda lock -f environment.yml --platform win-64 --platform linux-64
#   生成 conda-linux-64.lock：每行一个"URL+哈希"的精确下载指令
conda lock install -n ds-locked    # 按锁文件逐字节安装——与原环境逐包一致
# 典型用法：仓库里同时提交 environment.yml（人读）与 .lock（机器读），
# CI 上永远用 lock 装 → “在我机器上能跑”从物理上根除

13.4 conda-pack：把成品环境打包装运

bash 
# 源机：
conda install -n ds -c conda-forge conda-pack -y     # 工具本身装一次即可
conda pack -n ds -o ds.tar.gz                        # 打包整个环境（默认排除缓存与账本噪音）
# 目标机（同 OS 同架构！解到任意可写目录）：
mkdir -p ~/envs/ds && tar -xzf ds.tar.gz -C ~/envs/ds
~/envs/ds/bin/conda-unpack       # 修正压缩包里携带的绝对路径（Windows 跑 .bat 版）
source ~/envs/ds/bin/activate    # 用环境自带脚本激活——目标机可以根本没装 conda！
选择心法

跨平台给同事 → yml（--no-builds）；进 CI/生产、要逐哈希 → conda-lock；内网/断网/目标机无 conda、且 OS 架构一致 → conda-pack。三者不互斥：一份 yml 管人读、lock 管机器、pack 管应急。

图 13-1 三种复现手段的精确度-适用面对照

本章小结
  • yml 三种导出姿势语义不同：完整快照 / --from-history 配方 / --no-builds 跨平台。
  • channels 必须写进 yml，否则复现走样。
  • conda-lock 达到逐哈希级复现，CI 标配；conda-pack 免装 conda、整环境搬运，仅限同构机器。
  • 更新环境用 conda env update -f … --prune。

14.1 正式定义与场景

概念定义

离线部署指目标机器无法访问外网（生产隔离网、涉密网、船上、工控机）时，把 conda 安装器、包索引与包文件以“移动介质搬运”的方式投送过去并完成安装。核心三要素：安装器、repodata（索引）、包缓存（pkgs 目录）。

大白话

相当于“断网超市”：出不了门，就先在联网机上把整个货架按清单搬进硬盘（连带货架目录索引），再把硬盘带去孤岛开店。岛上的 conda 只需要把“频道”指向这个本地硬盘目录即可——它根本不在乎超市在互联网还是在 file:///。

14.2 方案一：本地目录频道（最常用）

bash · 联网机准备 → 移动硬盘 → 离线机安装 
#### A. 联网机上：把"需要的一切"下载进缓存 ####
conda create -n relay python=3.12 numpy pandas -y   # 干跑一遍，pkgs 缓存里就有了全套 .conda 文件
# 若要更全，可用 conda create --download-only（新版本支持只下载不安装）：
conda create -n relay2 --download-only python=3.12 scipy -y
# 打包缓存目录（Linux/macOS 路径示例；Windows 为 安装根\pkgs）
tar -czf pkgs-bundle.tar.gz -C ~/miniconda3 pkgs
# 连同离线安装器一起拷走：
#   Miniconda3-latest-Linux-x86_64.sh（或对应平台）

#### B. 离线机上：先装 Miniconda（安装器本身不需要网络）####
bash Miniconda3-latest-Linux-x86_64.sh -b -p /opt/miniconda3
# 解投送的缓存：
tar -xzf pkgs-bundle.tar.gz -C /opt/miniconda3        # 变回 /opt/miniconda3/pkgs

#### C. 断网使用：让 conda 只认本地缓存 ####
# 1) 清空网络频道，加上"本地缓存频道"：
conda config --remove-key channels
conda config --add channels file:///opt/miniconda3/pkgs
#    ↑ pkgs 缓存目录结构本身就符合频道规范（子目录即包、可索引）
# 2) 安装命令一切照旧，只是永远命中本地：
conda create -n prod python=3.12 numpy pandas -y
# 3) 大杀器：跳过求解直连缓存（应急；要求缓存里包完全齐备）
conda create -n prod --offline python=3.12 numpy pandas -y

14.3 方案二：conda-pack 成品直运（同构机器）

参见 13.4：联网机 conda pack -n ds -o ds.tar.gz，离线机解包 + conda-unpack 即用，目标机连 conda 都不需要。适合“几十台同配置工控机批量铺环境”。

14.4 方案三：内网私有频道（企业长期形态）

唯一出网点，安全可控；② 全员 .condarc 统一 channels 指向内网地址（运维下发）； ③ 新包走“代理机上 conda install → 自动进镜像”或私有频道（17章）；④ 版本审计有唯一台账，合规利器。 合规提醒：镜像 defaults 官方仓库再分发给内部多方使用，按 Anaconda 条款可能需要商业许可（17.3），镜像 conda-forge 则无此问题。

14.5 离线常见坑清单

常见误区

坑一：忘记搬“包的依赖”。联网机只装了 numpy 没装 scipy，缓存里自然没有 scipy 及其依赖——离线机要啥得在联网机清单里“预装/预下载”过。清单式管理：--download-only 逐项过一遍。

坑二：Windows 便携目录跨机激活失败。硬链接环境直接复制会坏（3 章）；要么 conda-pack，要么新机重建（指向本地缓存频道，秒级）。

坑三：本地频道忘了 conda index。自己攒的包目录没有 repodata 索引，conda 视它不存在——conda index 目录 补索引后才成频道。

本章小结
  • 三板斧按规模选：单机快用「本地缓存频道 + --offline」；同构批量用 conda-pack；企业长期用内网 HTTP 频道 + 统一 condarc。
  • 离线成败在联网机的清单完整性：--download-only 是保证手段。
  • 自定义包目录必须 conda index 才算频道；镜像 defaults 需留意许可条款。

第 15 章求解器、性能与缓存管理

15.1 正式定义

概念定义

conda 历史上出现过三代理求解器：classic（Python 原版逐层回溯，慢但语义严格）；libmamba（2022 年起默认，C++ 求解库，快一个数量级）；rattler（Rust 实现，conda 26.10 起成为新默认，还原生支持 conda-pypi 与更小的安装体积）。三者结果在绝大多数场景一致，个别边角案例 classic 更保守。

包缓存（pkgs_dirs）是所有环境共享的“收货区”（3 章）；硬链接让多环境复用同一份文件而不重复占盘；conda clean 负责回收缓存中的死包、索引与临时文件。

大白话

求解器换代像“人工验算→计算器→专业软件”：classic 是老会计打草稿，libmamba 是科学计算器，rattler 是装了数据库的专用软件。对你来说用法完全不变——只是快。而缓存像快递驿站：包裹先到驿站（pkgs），各环境凭单取走（硬链接），驿站满了就清（clean）。

15.2 慢的六大原因与对症下药

症状病因处方
Solving environment 转几十秒到几分钟SAT 规模大：频道多、版本约束松、历史环境复杂① 减频道（一环境一主频道）② spec 收紧（pkg=3.12）③ 升 conda 用新求解器 ④ 26.9+ --exclude-newer 截断候选
第一次永远慢、之后快repodata 索引冷缓存正常现象；保持索引缓存不清理（clean -i 慎用）

装完包 import 慢磁盘 io / 硬链接失效（跨盘安装）把 envs 与 pkgs 放同一盘（condarc 里 pkgs_dirs/envs_dirs）

15.3 clean 详解与磁盘回收

bash 
conda clean --help          # 四个对象看清楚再动手
conda clean -p               # 只清"未被任何环境链接"的死包（最安全，先跑这个）
conda clean -t               # 清 tarball/zip 缓存（= -a 的一半）
conda clean -i               # 清 repodata 索引缓存（⚠️ 下次联网操作会重新下载全量索引）
conda clean -l               # 清日志
conda clean -a               # 全清（= p+t+i+l）；磁盘告急时的标准大招
# 清前看战果预估（新版支持）：
conda clean --all --dry-run
# 环境本体减肥（环境内清理孤儿包，不动缓存）：
conda remove -n ds --unused
常见误区

误区：clean -a 会删掉我的环境。不会！clean 只动缓存（pkgs 里没被链接的部分、索引、日志），环境（envs/）分毫不动。真正会删环境的是 env remove。放心清。

误区：磁盘不够，把环境挪到移动硬盘。硬链接跨盘即失效，等于每个环境全量复制一份文件、且环境内绝对路径断裂。正确做法：先在 condarc 里把 envs_dirs/pkgs_dirs 设到大盘，再重建/新建环境。

第 17 章高级话题：conda-build 入门、许可合规与供应链安全

17.1 conda-build：把自己的代码打成 conda 包

概念定义

conda-build 把“源代码+配方（recipe）”加工成标准 .conda 包：配方文件 meta.yaml 声明名字、版本、依赖、构建脚本与测试；产出可直接 conda install 本地包文件 或推入私有频道。这是“团队内部分发自研工具”的正道。

yaml+bash · 最小可用的 meta.yaml 
# meta.yaml —— 配方三要素：package / build / requirements
package:
  name: mytool
  version: 1.0.0
source:
  path: .                # 源码就在当前目录（也可 git url+tag）
build:
  number: 0             # 构建号：同版本重打包时递增
  script: "{{ PYTHON }} -m pip install . -vv --no-deps"  # 常见：内部仍调 pip 打文件
requirements:
  host:
    - python
    - pip
  run:                  # 运行期依赖——装此包的人会自动得到它们
    - python >=3.10
    - numpy
test:
  imports:
    - mytool
bash 
conda install -n base -c conda-forge conda-build -y   # 工具装在 base（它是管理件）
conda build .                                          # 在配方目录执行 → 产出 .conda 包
# 本地试装：
conda install -n testenv /path/to/envs…/mytool-1.0.0-….conda
# 团队分发：产物丢进私有频道目录并索引：
conda index /data/pkgs

17.2 供应链安全：依赖投毒与防护

大白话

“投毒”=有人把恶意版本传上仓库，恰巧被你的宽松约束选中。2023 年 PyPI 与 conda 生态均出现过仿名包攻击。四层护甲：

  1. 锁死来源：生产环境 --override-channels + 私有频道，根本不碰公网。
  2. 锁死时间：conda ≥26.9 --exclude-newer 30d——新包先凉 30 天再进环境（官方为防投毒提供的正解）。
  3. 锁死身份：conda-lock 的哈希校验，下载文件与预期不符即报错。
  4. 锁死行为：敏感机器上 ssl_verify: true 永远开着；装包后的 post-link 脚本有执行权——只从可信频道装包是底线。

17.3 许可合规：Anaconda 商业条款要点 核对于 2026-11

条款要点（对日常工作影响最大的四条）

1）conda 软件本身开源免费（GitHub conda 组织治理），不受 Anaconda 公司条款约束。

2）defaults 频道（repo.anaconda.com/pkgs）受 Anaconda 服务条款约束：个人、认证大学的教学科研、员工少于 200 人的组织免费；≥200 人的商业组织任何用途需商业许可（2024-03 条款更新确立，2025-07 起新装 conda 内置 tos 插件命令行提示）。

3）conda-forge 等社区频道完全免费；Miniforge 安装器默认 conda-forge，全链路无许可风险。

4）镜像/再分发 defaults 大规模内容给第三方需要许可——企业内网镜像方案（14 章）部署前先过法务；镜像 conda-forge 无此问题。

大白话决策

自用/学校 → 随意，装什么都行；小公司（<200 人）→ 也可用 defaults；大厂无采购 → 全员 Miniforge + conda-forge 一劳永逸。拿不准时问法务，别在代码库里赌运气。

第 18 章最佳实践、学习路线与全书收官

18.1 十条黄金法则（浓缩全书）

  1. base 只住管家：业务环境一律另建；base 只升 conda 相关组件。
  2. 环境即项目：一个项目一个环境，命名可读（用途/项目名，拒绝 test/tmp）。
  3. 建环境必带 python=版本；换 Python 大版本 = 开新环境，绝不做原地大手术。
  4. 计划表必读：按 y 前扫一眼 NEW/SUPERSEDED/REMOVED，防“暗降级”。
  5. 一环境一主频道；个别包 频道::包名 点名；复现命令 --override-channels。
  6. conda 管大件，pip 补小件；pip 装过就别让 conda 再动同域；用 python -m pip。
  7. 导出即留底：环境定型就 conda env export；CI/生产上 lock；离线用 pack。
  8. 删前三问：名字对吗（env list）？留底了吗（export）？真不用了吗？
  9. 排错先归四水管：网络/求解/账本/权限；conda info + --show-sources + doctor 体检先行。
  10. 合规即工程：商业规模想清楚 defaults vs conda-forge 再动手。

下面对上表 10 条命令逐条详解（编号 T1-01～T1-10 与表格行一一对应）。每张卡片六个固定字段：术语定位（这条命令在专业上叫什么、是干什么的）、用途·大白话、关键参数与选项、执行后会发生什么、易出问题的地方、按实际项目替换（哪些要换、为什么换、换时注意什么）。

T1-01conda activate <环境名>
术语定位
环境激活（environment activation）：把指定环境设为“当前环境”的命令，属于 conda 环境管理的基本操作。
用途·大白话
进房间。把这个房间的门口揫到你终端 PATH 的最前面，从此你敲的 python、pip 都用这个房间里的东西。
关键参数与选项
只有一个参数：环境名。不带任何选项；名字必须是 conda env list 里出现过的那个。
执行后会发生什么
提示符前面多出 (环境名)；PATH 被改写（退出时还原）；激活脚本（若该环境有）会被执行。
易出问题的地方
报 “Run 'conda init'…” 说明当前终端没初始化过 conda（见 T4-01）；环境名写错报 EnvironmentLocationNotFound；PowerShell 首次使用报执行策略（第 2 章）。
按实际项目替换
把 <环境名>（连同尖括号）换成你的环境名，如 yf-sentiment。注意：环境名区分大小写、不能用路径斜杠；中文/空格名字在部分终端会出问题。替换后先用 conda env list 核对名字确实存在再激活。
T1-02conda deactivate
术语定位
环境退出（deactivation）：撤销当前激活、把环境从 PATH 里移出去的命令。
用途·大白话
退房间。退到外面一层（通常是 base 或纯 shell）；套了几层就连按几次，退到底。
关键参数与选项
无参数、无选项。
执行后会发生什么
提示符里的环境名消失（或变成外层环境名）；PATH 恢复成进入前的样子。
易出问题的地方
以为退一次就干净了（可能还在外层环境里）；退出后提示符乱套时，重开终端即可复位。
按实际项目替换
本条无占位符，无需替换，原样执行。
T1-03conda activate（空参数）
术语定位
回到默认环境：空参数的 activate 等于“直接回 base”，属于激活命令的特殊形式。
用途·大白话
一步回到管家房（base），省去连按 deactivate 的麻烦。
关键参数与选项
什么都不传。
执行后会发生什么
提示符变成 (base)；无论刚才套了几层，直接落在 base。
易出问题的地方
误以为这是“清空所有环境”（环境都还在，只是你人回了 base）；在 base 里随手装业务包是纪律大忌（第 18 章）。
按实际项目替换
无占位符，无需替换。
T1-04conda env list
术语定位
环境列举（environment listing）：列出本机所有已创建环境的命令。
用途·大白话
看全楼房型图：有哪些房间、星号标出你现在站在哪间。
关键参数与选项
无；等价写法 conda info --envs，两选一即可。
执行后会发生什么
打印环境清单：名字（或路径）+ 所在目录，当前环境带 *。
易出问题的地方
把星号误解成“默认环境”——它只表示“当前激活”；用 -p 建的路径环境在这里显示为路径而非名字。
按实际项目替换
无占位符，无需替换。建议把它当成“动手前对名字”的固定动作。
T1-05conda list [-n <环境名>]
术语定位
已安装包清单查询（package listing）：查看某环境内已安装包及其版本、构建号、来源频道的命令。
用途·大白话
查这个房间的账本：装了什么、什么版本、从哪家超市进的货。
关键参数与选项
-n 指定看哪个环境；不写就看当前激活的环境。附加开关：加 --revisions 看变更历史（回滚入口），加 pip 可只列 pip 装的部分（用法以 --help 为准）。
执行后会发生什么
一张表：Name / Version / Build / Channel；pip 装的包也会列出，Channel 列标 pypi。
易出问题的地方
把它当 pip list 用（pip 视角看不到 conda 包的构建号等细节）；忘了 -n，查了半天发现查的是当前环境不是目标环境。
按实际项目替换
可选项 -n <环境名>：查别的环境时才需要，换成那个环境的名字（区分大小写）；查当前环境时整段不要。表格里用管道符 conda list | grep pandas 能快速定位一个包（Windows 用 findstr）。
T1-06conda install [-n <环境名>] <包名>[=<版本>]
术语定位
包安装（package installation）：触发依赖求解、把包及其依赖装进目标环境的命令，是 conda 的核心事务操作。
用途·大白话
上货：给房间添一件家具，管家会顺带把它要求的全套都搬来。
关键参数与选项
-n 装到哪个环境（不写=当前环境）；<包名> 是频道里的正式名字；=<版本> 可选，可写区间（区间要整体加引号，如 "numpy>=2.1,<3"，防止 > < 被 shell 吞掉）。
执行后会发生什么
先转 Solving environment，然后出计划表（要下载什么、新增/替换/删除什么），等你确认 y 才真装。
易出问题的地方
忘写 -n，货上到当前环境（装错房间）；裸包名不锁版本，频道旧就装旧版；混过 pip 的环境再用 conda 动同域包会撞车（第 8 章）。
按实际项目替换
替换三处：<环境名>（目标环境名）、<包名>（注意 import 名 ≠ 包名，先 search 核实）、<版本>（按项目需求；数字别加引号）。替换后核对：计划表的 environment location 是否是你想要的环境。
T1-07conda search "<包名>>=<版本>"
术语定位
频道包检索（package search）：在已配置频道的索引里查可用版本的命令，不动手、只侦察。
用途·大白话
货架侦察：这个货有没有、能拿到哪些版本，再决定要不要买。
关键参数与选项
引号必须有（保护 > < 符号）；可加 -c <频道> 临时指定频道；可加 ="构建串" 按构建特征筛（如 mkl 变体）。
执行后会发生什么
列出候选：版本、构建号、所在频道；没找到会明说。
易出问题的地方
“找不到”≠不存在——可能频道没配（用 -c 临时试）、可能包名不对（conda 名与 import 名不同，第 6 章）。
按实际项目替换
换 <包名> 与 <版本>（版本可写区间也可不写）；引号必须保留。搜出来的版本号可直接复制进 install 命令的 = 后面，避免手打错。
T1-08conda run -n <环境名> <命令>
术语定位
免激活执行（run in env）：不改变你当前终端环境、直接在指定环境里执行一条命令的命令，常用于脚本和 CI。
用途·大白话
不进房间借手办事：人不动，让那个房间里的人替你跑一下。
关键参数与选项
-n 指定环境；后面接完整命令及其参数（如 python train.py）。输出控制相关选项以 conda run --help 为准（不同版本行为有差异）。
执行后会发生什么
命令在该环境里执行，输出回传到你当前终端；部分版本会把输出缓冲到命令结束才一次性吐出（长脚本看起来像卡住，属正常）。
易出问题的地方
拿它跑交互式命令（要输入密码/确认的）体验很差；以为 run 之后环境还激活着（它不改变你的终端状态）。
按实际项目替换
换两处：<环境名>（目标环境名）与 <命令>（连同它的参数，如 python train.py --epochs 3）。跑长任务前先拿 conda run -n 环境 python -c "import sys; print(sys.executable)" 验证执行者对不对。
T1-09python -m pip install <包名>
术语定位
PyPI 包安装（pip via Python）：用当前环境的 Python 调它自带的 pip、从 PyPI 装包的标准写法（严格说这是 pip 命令，因高频列入本表）。
用途·大白话
超市没货的小件上淘宝补：用 -m pip 这个写法保证装进“当前这个 python”的房间，不会装错地方。
关键参数与选项
-m pip 是关键（跟当前 python 走）；<包名> 后可加 ==版本 锁版本；可加 -r requirements.txt 批量装。
执行后会发生什么
pip 自己的输出（下载进度、安装清单），装进该环境的 site-packages。
易出问题的地方
裸敲 pip install 可能命中另一个环境的 pip（PATH 问题）——永远用 python -m pip；conda 装过的包别用 pip 重装同名（账本盲区，第 8 章）。
按实际项目替换
换 <包名>（PyPI 上的名字，pip 名与 import 名也常不同）；按需加版本号。注意确认执行前你在正确的环境里（看提示符）。
T1-10jupyter kernelspec list
术语定位
Jupyter 内核清单（kernel spec listing）：查看 Notebook 可切换的全部内核注册项的命令。
用途·大白话
看换班表：面板右上角能选到哪些“工人”（环境）。
关键参数与选项
无参数；相关命令 jupyter kernelspec uninstall <名> 删除某个注册项（只删排班表，不动环境本身）。
执行后会发生什么
列出每个内核的名字 + kernel.json 所在路径。
易出问题的地方
环境里装了 ipykernel 但没注册，这里就不会出现它（要按 T2-09 注册）；Notebook import 不到包时，先查这里看内核选对没有。
按实际项目替换
无占位符，无需替换。核对方法：清单里的名字应与目标环境名对得上。

T2-01conda create -n <名> python=<版本> [<包名>…] -y
术语定位
环境创建（environment creation）：新建一个独立前缀目录、装上指定 Python 与首批包的命令，是项目开房的标准动作。
用途·大白话
开新房间：定门牌、配一口锅，顺手把首批家具一次搬齐（一次求解，依赖关系一次协调好）。
关键参数与选项
-n 环境名（路径式改用 -p <路径>）；python=<版本> 强烈建议必写；方括号里的包名可写 0 个或多个；-y 跳过确认。
执行后会发生什么
求解→出计划表（若没 -y 则等你确认）→下载→落盘，最后提示你 conda activate 进去。
易出问题的地方
忘写 python=版本得到“空壳”环境；名字撞车报 EnvironmentLocationExists；交互终端里加 -y 会跳过计划表（新手建议不加，先看表再确认）。
按实际项目替换
换三处：<名>（建议带项目前缀，如 yf-xxx，见 19.9 命名规范；区分大小写）；<版本>（如 3.12，写主次即可，数字不加引号）；[<包名>…]（首批主力包清单）。替换后检查：conda env list 里出现新名字、activate 后 python -V 对得上。
T2-02conda env export [-f <文件.yml>]
术语定位
环境导出（environment export）：把环境现状写成 yml 菜谱的命令，复现与留底的入口。
用途·大白话
给房间拍快照存菜谱，以后照方抓药重建。
关键参数与选项
-f 写入文件（不写则打印到屏幕）；变体：--from-history 只记你点名过的包、--no-builds 去掉构建号（跨平台友好）。
执行后会发生什么
生成/打印 yml：环境名、频道列表、依赖清单（含 pip 装的 pip 小节）。
易出问题的地方
完整快照含平台专属包与构建号，直接丢给另一平台的人会装不上；忘检查 channels 是否写全（复现走样的头号原因）。
按实际项目替换
换 <文件.yml>：建议跟项目仓库走（如 ~/work/项目/environment.yml）；扩展名必须是 .yml；路径含空格时整体加引号。导出后建议打开着一眼 channels 小节。
T2-03conda env create -f <文件.yml> [-n <新名>]
术语定位
环境重建（create from spec）：照 yml 菜谱新建环境的命令，是“同事那边重建一套”的正道。
用途·大白话
异地照菜谱开一间同样的房间。
关键参数与选项
-f 菜谱路径；-n 可选，覆盖菜谱里 name 字段改名落地。
执行后会发生什么
逐项求解安装；完成后提示 activate 名字。
易出问题的地方
同名环境已存在报错（用 -n 改名）；菜谱里 channels 与本机镜像不一致时求解结果不同（先核对第 7 章频道设置）。
按实际项目替换
换 <文件.yml>（菜谱路径，相对/绝对均可，注意当前目录）；按需换 <新名>（CLI 里的 -n 优先级高于菜谱内 name）。建完用 conda list 和原环境抽插对比几个关键包版本。
T2-04conda env update -f <文件.yml> --prune
术语定位
环境增量同步（env update）：按 yml 把环境拉齐到菜谱状态的命令，可选用 --prune 清掉菜谱外多余的包。
用途·大白话
菜谱改了，让房间跟上：该补的补，开了 --prune 还会把菜谱里没有的乐西清出去。
关键参数与选项
-f 菜谱；--prune 是可选开关（不带则只加不减）。
执行后会发生什么
出计划表→确认→按菜谱补齐/卸除。
易出问题的地方
大坑：--prune 会把 pip 装的包（不在 yml 里）一并清掉；混装环境慎用 prune（第 8 章）。
按实际项目替换
换 <文件.yml>；是否保留 --prune 按环境是否“纯 conda 管理”决定。执行前建议先 export 一份留底（回滚保底）。
T2-05conda update <包名> [--dry-run]
术语定位
包升级（package update）：在已有环境内把指定包升到可选范围内最新版本的命令。
用途·大白话
给某件家具换新款；--dry-run 是先看购物清单不下单。
关键参数与选项
<包名> 可带版本约束；--dry-run 只出计划表不动手；可加 --all 升整环境（慎用）。
执行后会发生什么
求解后出计划表（升级/连带调整/可能的降级）；确认后执行。
易出问题的地方
不看 SUPERSEDED 降级区就按 y；在 base 里 update --all；升级 Python 本体引出半升级状态（第 6 章）。
按实际项目替换
换 <包名>；按需去留 --dry-run。升级前建议 export 留底，升级后跑一遍项目冒烟测试。
T2-06conda remove <包名>
术语定位
包卸载（package removal）：把包从当前环境移除，并连带卸掉“仅因它而装”的依赖的命令。
用途·大白话
退掉这件货，顺手把它带来的赠品也退了。
关键参数与选项
可加 -n 指定环境（否则当前环境）；可加 -y 跳确认；--force 蛮力模式仅排障用。
执行后会发生什么
确认后卸载，conda-meta 账本同步更新。
易出问题的地方
骨架包（python 等）拒绝卸——那是保护机制；误以为 remove 会把缓存也清掉（缓存归 clean，T3-04）。
按实际项目替换
换 <包名>（conda 名，不足 import 名）。执行后用 conda list | grep 包名 验收确实没了。
T2-07conda remove -n <环境名> --unused
术语定位
孤儿包清理（remove unused dependencies）：扫描环境中无人依赖的连带包并卸除的瘦身命令。
用途·大白话
扫房间里的孤儿件：当年因 A 进门、如今 A 走了没人认领的，请出去。
关键参数与选项
-n 指定环境；--unused 是开关本体。
执行后会发生什么
列出将卸的孤儿包清单，确认后执行。
易出问题的地方
误以为它会清缓存（它只动环境内部）；个别包你确实单独想要但从未被依赖，会被当孤儿请走——确认清单再按 y。
按实际项目替换
换 <环境名>。执行前 conda list 留个快照，万一误杀可照单重装。
T2-08conda install --revision=<N>
术语定位
环境修订回滚（revision rollback）：把环境整卷退回到第 N 次变更后状态的命令，是环境级“后悔药”。
用途·大白话
房间被今天乱七八糟的升级搞坏了？直接倒回到早上还健康的那一笔账。
关键参数与选项
--revision=N 的 N 从 conda list --revisions 输出里抄（rev 0 是出生点）。
执行后会发生什么
出一张“回退差异计划表”（该卸的卸、该装回来的装），确认后执行。
易出问题的地方
N 超出范围报错；回滚本身也是一次新修订（账本继续往后记）；pip 装的包不在账本里，回滚救不了它们（第 8 章）。
按实际项目替换
换 <N>（纯数字，不带引号）。替换前务必先跑 conda list --revisions 对准编号——抄错号等于回错版本。
T2-09python -m ipykernel install --user --name <名> --display-name "<显示名>"
术语定位
内核注册（kernel registration）：把当前环境登记进 Jupyter 内核清单、供 Notebook 切换的命令，是“面板-内核分离架构”（第 11 章）的落地动作。
用途·大白话
给 Notebook 的换班表添一名新工人：以后面板右上角能选到这个环境。
关键参数与选项
--user 注册到当前用户级（不动系统）；--name 内核标识（英文、无空格， uninstall 时用它）；--display-name 面板上显示的名字（可中文，整体加引号）。
执行后会发生什么
写入一份 kernel.json；jupyter kernelspec list 随即出现该内核。
易出问题的地方
--name 重名会覆盖旧注册；装完包 import 不到时忘了重启内核（已加载模块不热更新）；前提是该环境已装 ipykernel（conda install ipykernel）。
按实际项目替换
换两处：<名>（建议与环境名一致，便于对账；仅小写字母数字连字符）与 <显示名>（引号不能丢）。替换后检查：kernelspec list 里出现，且 Notebook 内 sys.executable 指向该环境。
T2-10conda install <频道>::<包名>[=<版本>]
术语定位
频道限定安装（channel-qualified spec）：用三明治语法强制“这个包必须从指定频道来”的写法，属于 spec 写法而非独立命令。
用途·大白话
点名“这袋盐必须去某家超市买”，不管你偏好卡上怎么排序。
关键参数与选项
<频道> 用短名（如 conda-forge，可被 channel_alias 映射到镜像）；:: 是分隔符；版本可选。
执行后会发生什么
求解时这个包绕过频道优先级排序，锁死从指定频道取。
易出问题的地方
频道名拼错报找不到；把它用于长 URL（标准短名写法最稳，URL 式用 -c 更顺）；环境整体仍受频道优先级管（只这一个包被点名）。
按实际项目替换
换 <频道>（标准短名，区分大小写）与 <包名>；按需加版本。替换后从计划表 Channel 列核对该包确实来自指定频道。
T2-11conda search --info <包名>
术语定位
包元数据详情查询（search with info）：在检索结果上叠加依赖、约束、摘要、许可证等元数据的命令。
用途·大白话
深挖一件货的详细说明书：它需要什么、能配什么、许可证允不允许商用。
关键参数与选项
<包名> 可带 =版本 看具体那个版本；输出较长注意翻页；可用 -c 限定频道。
执行后会发生什么
结构化详情：依赖列表、版本约束、构建串、许可证等。
易出问题的地方
不同频道同包可能各有一份详情（先想清楚查的是哪家）；用它代替不了 install 前的计划表阅读。
按实际项目替换
换 <包名>（可带版本）。抄写依赖版本时直接复制粘贴，别手打。

官方命令模板大白话：这句在对谁说什么占位符与注意事项
conda rename -n <旧名> <新名>给房间换门牌（不动内部东西）路径环境用 -p <旧路径> 传旧名
conda create -n <新名> --clone <旧名>克隆一间一模一样的房间做实验大环境克隆要等硬链接，磁盘不会翻倍（第 3 章）

conda pack -n <名> -o <文件.tar.gz>把成品房间整个打包带走第三方工具 conda-pack；目标机同 OS 同架构，解包后跑 conda-unpack
conda config --add channels <频道URL>
conda config --append channels <频道URL>
conda config --set <键> <值>		改购物偏好卡：头插超市 / 尾插备胎超市 / 改单项设置--add 变最高优先级、--append 变最低；改前先 --show-sources 定位（第 7 章）
conda lock -f <yml> --platform <平台>
conda lock install -n <名>		生成 / 安装逐哈希锁盒第三方工具 conda-lock；平台如 win-64/linux-64；CI 标配（第 13 章）
conda install --exclude-newer <日期> <包名>只考虑某日期前上架的货（安全+复现+提速）conda ≥26.9；语义细节见第 15 章
conda env config vars set <KEY>=<值>
conda env config vars list / unset <KEY>		给房间配专属环境变量（激活时生效）conda ≥4.8；写在环境里，删环境即消失
conda list --explicit --md5 > <文件>导出「URL+哈希」极简锁清单消费端 conda create -n <名> --file <文件>（格式自动识别）；官方内置功能，免装第三方

下面对上表 10 条命令逐条详解（编号 T3-01～T3-10 与表格行一一对应，字段含义同前）。

T3-01conda rename -n <旧名> <新名>
术语定位
环境重命名（environment rename）：在不动环境内部任何文件的前提下给环境改名的命令。
用途·大白话
给房间换门牌，里面的东西原封不动。
关键参数与选项
-n 旧名 新名 两个位置参数；路径环境用 -p <旧路径> 传旧名。
执行后会发生什么
envs/ 下目录改名、账本更新；完成提示。
易出问题的地方
老版本 conda 无此命令（只能 clone+remove 两步）；新名已存在报错；别名改名不改“引用”——见替换字段。
按实际项目替换
换 <旧名> 与 <新名>（均区分大小写）。关联位置检查：引用旧环境名的地方要同步改——IDE 里选的解释器路径、Jupyter 内核注册（kernelspec 里的 kernel.json 指向路径）、启动脚本里的 activate 行、CI 配置。改完逐一验证。
T3-02conda create -n <新名> --clone <旧名>
术语定位
环境克隆（environment cloning）：复制一份一模一样的环境作为新名字的命令，实验/备份场景专用。
用途·大白话
复制一个平行房间：在副本里随便折腾，原件无损。
关键参数与选项
--clone 后接被克隆环境（名或路径均可）；新名用 -n。
执行后会发生什么
从包缓存硬链接复制一份环境（磁盘不会翻倍）；完成后提示 activate 新名。
易出问题的地方
中途断电留半个新环境（删掉重克隆）；克隆不会带走“环境级环境变量/配置”（部分设置需重新设，具体范围随版本 → 待核实）。
按实际项目替换
换 <新名>（建议加 backup/test 后缀）与 <旧名>。克隆后 activate 新环境跑一下项目入口验证完整性。
T3-03conda env remove -n <名>
术语定位
环境删除（environment removal）：把整个环境目录连同账本一并移除的命令。
用途·大白话
拆房间：整间清空退租。
关键参数与选项
-n 名字（路径式用 -p）；可加 -y 跳确认。
执行后会发生什么
确认后删目录；包缓存里对应包还在（clean 前可秒重建同名环境）。
易出问题的地方
删错无法撤销；IDE/Jupyter 还留着指向它的注册/配置，需手动清理；名字手滑拼错删错环境。
按实际项目替换
换 <名>。删前三问（第 18 章）：env list 对名字？export 留底了吗？真不用了吗？删后检查：kernelspec list、IDE 解释器选择页里有没有指向已删环境的残项。
T3-04conda clean -p | -t | -a [-d]
术语定位
缓存清理（cache cleaning）：回收包缓存/索引/日志中不再被引用部分的命令，不动任何环境。
用途·大白话
清驿站：没人取的包裹、拆完的纸箱、过期台账扫出去。
关键参数与选项
-p 只清“未被任何环境链接”的死包（最安全）；-t 清 tar 包；-a 全清（含 -i 索引、临时文件、日志）；-d 预演只出清单不动手。
执行后会发生什么
报告将释放的空间并执行；-d 只打印清单。
易出问题的地方
误以为会删环境（不会）；-i 清索引后下次联网操作要重新下载全量索引（慢一次）；-f（force-pkgs-dirs）是危险项，会断硬链接环境，别当普通清理用。
按实际项目替换
无占位符，无需替换。磁盘告急顺序：先 -p、再 -t、最后才 -a；拿不准先加 -d 预演。
T3-05conda pack -n <名> -o <文件.tar.gz>
术语定位
环境整包搬运（conda-pack，第三方工具）：把已装好的环境连同解释器打成 tar 包的命令，离线交付手段之一（第 13 章）。
用途·大白话
把做好的整桌菜原样端走，对方锅灶型号得和你一样（同 OS 同架构）。
关键参数与选项
-n 被打包环境；-o 输出文件；前提：工具本身已装（conda install conda-pack）。
执行后会发生什么
生成 tar.gz；目标机解包 + conda-unpack 修路径后即用，目标机不需要 conda。
易出问题的地方
跨 OS/架构不可用；忘跑 conda-unpack 导致路径残留；混装 pip 包的环境打包时部分包兼容性需实测（待核实，以你版本实测为准）。
按实际项目替换
换 <名> 与 <文件.tar.gz>（输出路径建议带环境名+日期，方便对版本）。交付前在目标机跑入口脚本验收。
T3-06conda config --add channels <频道URL> / --append / --set
术语定位
配置项管理（config management）：增改 .condarc 频道列表与单项设置的命令族（三个动词三个用途）。
用途·大白话
改购物偏好卡：--add 是把一家超市提到最优先，--append 是加到末尾当备胎，--set 是改某一项设置。
关键参数与选项
--add 频道 头插（优先级升高）；--append 频道 尾插（最低）；--set 键 值 单项；配套：--show-sources 看配置来自哪份文件。
执行后会发生什么
写入 .condarc；下次求解即按新顺序/新设置。
易出问题的地方
add 与 append 分不清导致优先级反了；同一频道重复添加产生重复条目；改错了那份 condarc（多份叠加时先 --show-sources）。
按实际项目替换
换 <频道URL>（镜像地址以镜像站/项目组下发文档为准——地址会变，属待核实性质，配前核对）与 <键><值>。改后用 conda config --show channels 验证顺序。
T3-07conda lock -f <yml> --platform <平台> + conda lock install -n <名>
术语定位
锁文件生成与安装（conda-lock，第三方工具）：按平台生成逐哈希锁文件、再按锁安装的命令对，CI/生产级复现标配（第 13 章）。
用途·大白话
生成“中央厨房预制盒”（连食盐克数都锁死）；install 就是拆盒上架，逐字节一致。
关键参数与选项
-f 菜谱；--platform 可重复传多个（每平台各生成一份 .lock）；install -n 按锁装到环境。
执行后会发生什么
生成 conda-<平台>.lock；install 时逐行“URL+哈希”安装，不重新求解。
易出问题的地方
平台名写错不生成；锁过时（菜谱变了）要重新生成；需先装 conda-lock 工具本身。
按实际项目替换
换 <yml>（菜谱路径）、<平台>（标准 subdir 名：win-64/linux-64/osx-arm64 等，不能自造）、<名>（目标环境名）。锁文件建议入仓库并在 README 标明生成时间。
T3-08conda install --exclude-newer <日期> <包名>
术语定位
时间截断求解（exclude-newer）：只考虑某日期前发布的包版本的选项，安全/复现/提速三重价值（第 15 章）。conda ≥26.9
用途·大白话
新包先凉一阵再进门：今天刚上架的不买，只买“出厂满月”的。
关键参数与选项
<日期> 写成 ISO 形如 2026-08-01；可与 create/install/update 同用。
执行后会发生什么
求解时把发布时间晚于该日期的包排除出候选。
易出问题的地方
它不是安全保证（旧包伪造时间戳可绕过，官方明示“尽力而为”）；具体冷却天数无官方统一标准（按团队约定定，待核实）。
按实际项目替换
换 <日期>（截止日按团队策略定，格式 YYYY-MM-DD）与 <包名>。替换后从计划表核对拿到的版本发布日期早于截止日。
T3-09conda env config vars set <KEY>=<值> / list / unset
术语定位
环境级变量管理（env config vars）：把环境变量写进环境本身，激活时自动生效的命令族。conda ≥4.8
用途·大白话
给房间贴一张“进门须知”：每次进这间房，某变量自动设好（如项目根路径）。
关键参数与选项
set 时 KEY=值 成对；list 查看；unset KEY 删除；只对当前环境生效。
执行后会发生什么
写入环境内配置；重新 activate 后变量才在环境里可见（echo 或 env 查验）。
易出问题的地方
设完不重激活以为没生效；和 shell 变量混淆（这它是跟环境走的）；KEY 命名属项目约定，官方无标准字段（待核实：按项目 README 约定）。
按实际项目替换
换 KEY 与值（如 PROJECT_ROOT=/data/work/yf-sentiment）；路径在 Windows 上注意盘符与斜杠方向（可用正斜杠）。设完 activate 后 echo 验证。
T3-10conda list --explicit --md5 > <文件>
术语定位
显式锁清单导出（explicit spec export）：把环境导成“每行一个 URL+MD5 哈希”极简锁文件的命令，官方内置、免第三方工具。
用途·大白话
开一张采购回执：每行都是“去哪个货架、拿哪个批次”的硬清单。
关键参数与选项
--explicit 逐行列出；--md5 附校验哈希；> <文件> 是 shell 重定向（Windows 下同样可用）。
执行后会发生什么
生成纯文本清单；消费端 conda create -n <名> --file <文件>（新版可自动识别格式；旧版用 -f，兼容差异 → 待核实：以你版本 --help 为准）。
易出问题的地方
清单里 URL 是平台专属的（win 导出的 Linux 用不了）；镜像换地址后旧清单可能拉不到货。
按实际项目替换
换 <文件>（建议入仓库版本管理）。消费时换目标环境名；跨平台重建请改用 yml/conda-lock（第 13 章）。

T4-01conda init <shell名> / conda init --reverse
术语定位
shell 初始化（shell initialization）：把 conda 的激活逻辑写进某种终端的启动脚本的命令；--reverse 是还原初始化。
用途·大白话
教会某种终端“看见 conda”：以后任意开这种终端都能 activate；--reverse 是教会的东西收回来（出厂状态）。
关键参数与选项
<shell名>：bash、zsh、cmd.exe、powershell（按你实际用的填）；--reverse 还原（卸载前清理用，第 2 章）。
执行后会发生什么
修改 shell 启动脚本（如 ~/.bashrc、~/.zshrc）；必须重开终端才生效。
易出问题的地方
改完不重开终端以为没生效；PowerShell 首次遇执行策略报错（第 2 章 2.2）；对已初始化 shell 重复 init 一般幂等但输出多余片段。
按实际项目替换
换 <shell名>（不确定自己用什么 shell：Linux/macOS 跑 echo $SHELL，Windows 看窗口标题或你用的程序名）。执行后新开一个终端验证提示符出现 (base)。
T4-02conda self-update
术语定位
管理器自升级（self-update）：把 base 里的 conda 本体升到新版本的命令。conda ≥26.5
用途·大白话
管家自己给自己升职级：不动业务环境。
关键参数与选项
无参数；老版本等价写法 conda update -n base conda。
执行后会发生什么
升级 conda 本体与必要组件；完成后 conda --version 变化。
易出问题的地方
老版本没有 self-update（报 Unknown command）；升级后个别插件/自定义脚本兼容性需重新验证（第 17 章插件）。
按实际项目替换
无占位符，无需替换。升级后建议跑一次 conda info 与一条小事务验证功能正常。
T4-03conda info / conda info --json
术语定位
状态总览（information）：一页展示频道、求解器、环境目录、缓存位置、平台等全局信息的命令，排错第一步。
用途·大白话
管家的自我介绍：我是几版、住哪、去哪买菜、收货区在哪。
关键参数与选项
--json 机器可读格式（给脚本消费）；无其他必选参数。
执行后会发生什么
打印全局状态页。
易出问题的地方
排错不看它直接猜（频道顺序、缓存位置都能在这里发现异常）；看 conda info 时忽略 active env 行（它同时告诉你当前环境）。
按实际项目替换
无占位符，无需替换。提问求助时把这份输出附上。
T4-04conda doctor
术语定位
环境体检（health check）：检查硬链接完整性、环境内部结构健康度的诊断命令。较新版本提供
用途·大白话
给整套系统做体检：哪里断链、哪里缺件，出报告不动手修。
关键参数与选项
可指定环境（选项细节以 conda doctor --help 为准）。
执行后会发生什么
列出发现的问题（丢失文件、损坏链接等）。
易出问题的地方
指望它自动修复（它是诊断不是治疗；修复靠重装/回滚）；老版本无此命令。
按实际项目替换
无占位符（指定环境时换环境名/路径）。体检后对照报告决定重装或 revision 回滚。
T4-05conda create -n <名> --download-only python=<版本> [<包>…]
术语定位
预下载填缓存（download-only）：完成求解与下载但不落环境的命令，离线部署第一步（第 14 章）。
用途·大白话
只把货全订到驿站，不往房间搬——为后续离线安装备货。
关键参数与选项
其余同 create；--download-only 是核心开关（会取消链接事务）；临时环境名可随便。
执行后会发生什么
包缓存（pkgs）被填满；环境并未创建；退出提示类似 “Package caches prepared”。conda env create -n relay --download-only … 也是同样用法。
易出问题的地方
以为装好了（实际什么都没装）；清单漏包——离线机要装而没预下载的包直接报找不到。
按实际项目替换
换 <名>（临时名如 relay）、<版本> 与包清单。清单完整性是成败关键：把目标机将来要装的所有包/版本全部列上；下载后核对缓存目录内容再拷走。
T4-06conda install --offline <包名>
术语定位
离线安装（offline installation）：完全不联网、只从本地包缓存求解并安装的选项，断网机上的交付手段（第 14 章）。
用途·大白话
只在驿站里取货装房间，一概不出门。
关键参数与选项
--offline 开关；可与 create/install 同用；<包名> 必须在本地缓存里齐备。
执行后会发生什么
从缓存硬链接安装（快）；缓存缺货直接报找不到。
易出问题的地方
与 --download-only 没配对好（预下载漏包）；以为 offline 会顺便清缓存（不会）。
按实际项目替换
换 <包名>（及版本）——必须与联网机预下载清单一致，多一个字符都对不上。执行后 conda list 验收。
T4-07conda build <配方目录>
术语定位
包构建（conda-build，第三方工具）：把源代码+meta.yaml 配方加工成标准 .conda 包的命令，自研分发正道（第 17 章）。
用途·大白话
把自家产品按行业标准装箱、贴标，变成谁都能 conda install 的货。
关键参数与选项
位置参数是含 meta.yaml 的目录；前提：conda-build 已装（装在 base，属管理件）。
执行后会发生什么
按配方执行构建脚本→测试→产出 .conda 到包缓存目录。
易出问题的地方
配方里版本/依赖写错构建失败；构建脚本里平台差异（脚本写法参考第 17 章 meta.yaml）。
按实际项目替换
换 <配方目录>（含 meta.yaml 的路径，相对/绝对均可，注意当前目录）。构建后用临时环境试装一次再发布。
T4-08conda index <目录>
术语定位
本地频道索引生成（index generation）：给本地包目录生成 repodata 货架清单、使其成为可用频道的命令。该命令由 conda-build/conda-index 生态工具提供，随版本归属有变动 待核实：以你版本 --help 为准。
用途·大白话
自己攒的仓库没有台账不算超市：这一步就是给台账盖章。
关键参数与选项
位置参数是包所在目录；需先装对应工具。
执行后会发生什么
目录里生成 repodata 索引文件；之后 -c 该目录即可安装其中的包。
易出问题的地方
忘 index 导致 conda “看不见”本地频道；新增包后忘了重新 index（清单不更新）。
按实际项目替换
换 <目录>（本地包目录或 HTTP 目录；Windows 路径含空格加引号）。index 后用 conda search -c 目录路径 包名 验收。
T4-09conda config --env --set <键> <值>
术语定位
环境级配置写入（per-env config）：把一条设置写进当前环境而非用户级 .condarc 的选项，与“一次性 vs 每项目”划分直接相关（19.8）。
用途·大白话
把一条偏好贴在某个房间门上，只影响这间房。
关键参数与选项
--env 指定写入当前环境；--set 键 值 同普通 set；先 conda config --describe 键 查键含义。
执行后会发生什么
环境目录里生成 condarc；该环境内配置优先于用户级（近者覆盖远者）。
易出问题的地方
以为是全局设置（只影响这个环境）；删环境即消失；与 --env 之外的 --set 弄混（后者写用户级）。
按实际项目替换
换 <键><值>（可用键以 conda config --describe 列出的为准，勿自造）。设置后 activate 里外各跑 config --show 键 对比差异。
T4-10conda update -n base --all
术语定位
base 整体升级（update all in base）：把 base 环境整套包升级到最新的命令，仅适合 Anaconda 发行版用户。
用途·大白话
全家桶整体换新——仅当你 base 里真的是原厂全家桶时才该这么干。
关键参数与选项
-n base 明确目标（防止误升当前环境）；--all 全部包。
执行后会发生什么
出大计划表（大量 SUPERSEDED），确认后整环境升级。
易出问题的地方
base 里装过业务包/ pip 包后这么升报冲突或乱套（纪律：base 极简）；把它跑在业务环境（应只升单包，T2-05）。
按实际项目替换
无占位符，无需替换，但执行前先确认 base 未被污染（conda list 看一眼）。

T5-01conda commands
术语定位
子命令枚举（command enumeration）：让当前安装的 conda 自报家门，列出它支持的全部子命令的命令。
用途·大白话
问管家“你都会哪些本事”，得到的清单因版本而异。
关键参数与选项
无参数。
执行后会发生什么
打印子命令清单（含插件贡献的命令）。
易出问题的地方
拿网上旧清单对照以为缺命令（以本机这份为准）；它在老版本可能不可用。
按实际项目替换
无占位符，无需替换。发现陌生命令后用 命令 --help 接着查。
T5-02conda compare -n <环境名> <environment.yml>
术语定位
环境对账（compare to spec）：拿环境现状与菜谱逐项对比、报告差异的命令。
用途·大白话
拿账本和菜谱对账：“说好的三件家具怎么少了一件/多了一件/型号不对”。
关键参数与选项
-n 环境名；位置参数是 yml 文件；细节以 conda compare --help 为准（各版本输出格式有差异，待核实）。
执行后会发生什么
列出差异（缺失/多余/版本不一致）。
易出问题的地方
把它当校验器（它只报告不修复）；混装环境里 pip 部分不在对比范围（第 8 章）。
按实际项目替换
换 <环境名> 与 <environment.yml>（菜谱路径）。排查“同事那能跑我这不能跑”时第一步对账。
T5-03conda export --format=requirements
术语定位

术语定位

用途·大白话
不用驿站代发，直接把整箱货复制进房间（多占盘，但稳）。
关键参数与选项
--copy 开关；与 create 也可同用。

术语定位

用途·大白话
给隔壁楼的房间配菜：算得出、装得下，但你在本机进不去用不了（解释器是别的平台的）。
关键参数与选项
--subdir 标准平台名（win-64/linux-aarch64/win-arm64 等，不能自造）；其余同 create。
执行后会发生什么

易出问题的地方
以为能在本机激活运行（不行）；平台名写错报无包。
按实际项目替换
换 <平台名>（用标准 subdir 枚举名）与 <名><版本>。用途：为 ARM 交付机准备 Linux 环境再 conda-pack 运走。
T5-10conda activate <全路径> / conda env remove -p <路径>
术语定位
路径环境操作（prefix-based ops）：对用 -p 创建的“路径环境”的激活与删除，能力与 -n 式完全对等，只是引用方式不同。
用途·大白话
对自建别墅：报完整地址来进出/拆除。
关键参数与选项
激活时直接给路径；remove/delete 用 -p；创建时也是 conda create -p 路径。
执行后会发生什么
与名字式效果一致：PATH 改写/目录删除。
易出问题的地方
路径写错（Windows 盘符、反斜杠与引号）；删错路径无法撤销（比名字式更危险——路径直接指向磁盘目录）。
按实际项目替换
换 <全路径>/<路径>：Windows 下含空格整体加引号、盘符大小写不敏感但建议统一大写；Linux/macOS 注意 ~ 展开与权限。删除前先 ls 目录确认内容再执行。

19.8 一次性配置 vs 每个项目配置

概念定义

conda 的配置存在三个层级：机器/系统级（系统 condarc，全员生效）、用户级（~/.condarc，跟着你的账号走）、环境级（环境内 condarc 与 env vars，跟着环境走）。判断一条配置属于哪类，问一句：“换一个项目/换一台机器，它还该跟着我吗？”

一次性配置（装机/接入项目时做一次，跨项目共享，写进用户级 .condarc 或 shell）
配置做什么何时做/频率
conda init <shell>让终端认识 conda（激活能力）装机一次
channels 镜像列表固定从哪个超市进货（国内镜像/项目组镜像）装机一次；镜像站换地址才改
channel_alias / default_channels短名频道映射到镜像（如 conda-forge → 项目组镜像）装机一次
envs_dirs / pkgs_dirs房间和驿站迁去大盘装机一次；同盘才硬链接省盘（15 章）
solver / channel_priority选求解器、锁 strict 模式装机一次（15/7 章）
ssl_verify内网自签证书路径装机一次（内网环境）
create_default_packages: [pip]每次建环境自动带上 pip（可选逆性便利）装机一次

上表逐条说明（一次性配置，第 1–8 行）：为什么它们是“一次性”、要替换什么。
  1. conda init <shell>：教终端认 conda，跟项目无关所以装机一次。替换 <shell> 为你实际终端名；重开终端验证。
  2. channels 镜像列表：固定“去哪家超市”，所有项目共享。替换为镜像 URL——镜像地址随镜像站迁移会变，配置前以镜像站帮助页/项目组文档为准（待核实性质）；改后 conda config --show channels 验证顺序。
  3. channel_alias / default_channels：让 conda-forge 等短名自动映射到镜像，避免逐个频道写长 URL。替换值同镜像地址；改后用一条 search 验证短名能解析。
  4. envs_dirs / pkgs_dirs：房间与驿站迁去大盘，防止家目录爆。替换为你的可写大盘路径（注意权限与同盘硬链接，第 15 章）；改后新建一个环境验证落在新目录。
  5. solver / channel_priority：选求解器、锁 strict。值不用替换（rattler/strict 即推荐值）；老版本可用值以 --describe 为准。
  6. ssl_verify：内网自签证书场景配证书路径（或保持 true）。替换为证书文件路径；关成 false 属临时排障手段，勿长期。
  7. create_default_packages: [pip]：建环境自动带 pip（可选便利）。内容按需增减（如补 ipykernel）；注意这会影响所有新建环境。
  8. conda self-update：管家保养，与项目无关。无占位符；周期性执行即可。

上表逐条说明（每项目配置，第 1–8 行）：什么时候做、要替换什么、要检查哪里。
  1. conda create -n <项目环境> python=<版本>：立项开房。替换环境名（建议“项目前缀-用途”，如 yf-sentiment，区分大小写）与版本；建后 activate + python -V 验收。
  2. conda install <包>=<版本>：依赖定型，spec 带版本保证复现。替换包名与版本（版本以 search 结果为准）；装后计划表/conda list 双验收。
  3. ipykernel 注册：让 Notebook 能选到本环境。替换内核名与显示名（T2-09）；注册后 kernelspec list 检查出现。
  4. conda env export -f environment.yml：环境快照入仓库。替换输出路径（跟仓库走）；导后抽检 channels 小节。
  5. conda env config vars set <KEY>=<值>：项目专属变量（如 PROJECT_ROOT）。KEY 名属项目约定无官方标准（待核实：按项目 README）；设后重激活验证。
  6. conda config --env --set <键> <值>：只影响该环境的配置覆盖。键用 --describe 列出的合法键（勿自造）；删环境即失效。
  7. conda list --revisions：自动记的变更账本，无需配置；出事时配 --revision=N 回滚（N 抄自输出）。
  8. conda env remove -n <项目环境>：结项拆房。删前 export 留底、env list 对名；删后清理 IDE 解释器指向与 kernelspec 残项。
常见误区

误区：把项目组镜像写进某个环境的 condarc 里当“项目配置”。镜像属用户级一次性配置；把频道写进环境级会导致换机器重建环境时频道丢失、复现走样。频道类信息要么用户级、要么写进 yml 的 channels 小节随仓库走。

误区：新机器上重新发明所有配置。老手做法：把 .condarc 存进个人 dotfiles 仓库，新机一条 conda init + 拷回 condarc 即完成全部一次性配置。

19.9 工程实例：虚拟项目「云帆」的一年

虚构声明（虚拟项目情境）：「云帆」是一个用于教学的虚构数据项目（项目组自用域名示例 yunfan.example.com），人物、机器名、环境名、包名均为示例，前后一致，可整套照抄演练；现实中请把 yunfan.example.com 换成你项目组/组织的真实镜像地址（思路同 <尖括号> 占位符）。选择虚拟项目而非虚拟公司：避免与企业许可、组织规模等话题纠缠，情境更通用（团队、课程、开源项目均适用）。示例环境：Linux x86_64 工作站，Miniconda 装于 ~/miniconda3。

场景 C：日常循环 + 一次事故救火

bash · 日常与救火（小李）

20·T1-01conda --version
用途与适用场景
官方定位：显示 conda 自身版本号；场景：装完 conda 的第一句验收、排障或向人求助时报环境的第一句话。大白话：问管家"你是几"。
官方写法
conda --version，或简写 conda -V；无必填参数、无可选项。
通俗解释
终端打印一行类似 conda 26.x。有没有装对、PATH 配没配好，一条命令见分晓。
典型用法
装机后验收；发帖提问前先报版本（见本组示例对照第 ① 条）。
注意事项
报 conda: command not found 说明未安装或 shell 未初始化（回第 2 章）；简写是大写 -V，小写 -v 不是这个意思。
20·T1-02conda --help
用途与适用场景
官方定位：列出 conda 全部子命令清单及一句简介；场景：忘命令名时先翻它。大白话：让管家自报会哪些本事。
官方写法
conda --help，或简写 conda -h；无参数。
通俗解释
屏幕上列出所有子命令名和一行说明——这就是 conda 的"菜单"。
典型用法
想不起"删环境"是 remove 还是 env remove 时，先扫这份清单再查下一张卡的详细帮助。
注意事项
清单随版本不同，以本机输出为准；它只给命令名，具体参数要看下一张卡。
20·T1-03conda <子命令> --help
用途与适用场景
官方定位：查看单个子命令的完整帮助（参数、默认值、示例）；场景：写命令前确认参数真的存在。大白话：翻某一条命令的完整说明书。
官方写法
conda <子命令> --help；<子命令> 替换为 create、install、env、remove 等；可简写 -h。
通俗解释
比上网搜更快、且和本机版本严格对得准的"说明书"。抄来的网文命令先在这里验明正身。
典型用法
conda create --help 确认有没有 --clone 这个参数（见本组示例对照第 ③ 条）。
注意事项
若某参数在这里找不到，它多半不存在（版本差异除外）——别把"参数不存在"误判成"环境坏了"，存疑命令见 20.6。
20·T1-04conda info
用途与适用场景
官方定位：显示 conda 全局状态（安装路径、当前环境、频道配置、缓存目录、平台信息）；场景：排错第一步。大白话：管家的自我介绍——住哪、你站哪间房、进货超市在哪、驿站在哪。
官方写法
conda info；常用可选项 -e（等价环境列表，见 T4-13）、--json（机器可读版，见 T4-01）。
通俗解释
一屏看清"环境地基"：conda 装在哪个目录、当前激活的是哪间、频道顺序对不对、缓存盘在哪。
典型用法
镜像配完看 channel 小节验收；磁盘吃紧看 package cache（见本组示例对照第 ④ 条）。
注意事项
字段多，新手重点看 active env、channel、package cache 三处；输出与配置文件一一对应，改配置后用它复核。
20·T1-05conda env list
用途与适用场景
官方定位：列出本机所有 conda 环境及所在路径，星号标当前环境；场景：切环境前先对名。大白话：看全楼房型图，* 是你现在站的那间。
官方写法
conda env list；可选项 --json（给脚本用）。
通俗解释
打印一张环境清单：名字＋完整路径，当前激活的环境前带星号。
典型用法
环境多时过滤：conda env list | grep "<前缀>"（Windows 用 findstr "<前缀>"）。
注意事项
base 也是一间房，别把全家桶当业务环境用（第 5 章）；路径式环境在这里显示的是路径而非名字。
20·T1-06conda activate <环境名>
用途与适用场景
官方定位：激活指定环境，使其成为当前 shell 的默认 Python；场景：做任何安装/运行前的第一步。大白话：进房间——提示符挂上房间名，此后 python/pip 都用它。
官方写法
conda activate <环境名>；或 conda activate <全路径>（激活 -p 创建的路径式环境）。
通俗解释
激活后提示符前面出现环境名，例如 (demo)——这是你站对房间的唯一凭据。
典型用法
conda activate demo 之后立刻 python -V 验收（见本组示例对照第 ⑥ 条）。
注意事项
环境名区分大小写；报 Run 'conda init' 说明 shell 未初始化，先执行 conda init <shell> 重开终端（第 2 章）；PowerShell 首次需放开执行策略（第 2 章）；换环境不必先退，直接 activate 新名。
20·T1-07conda deactivate
用途与适用场景
官方定位：退出当前激活的环境，回到上一级（通常 base）；场景：收工、切换前整理。大白话：退房间——连按几次可退到底。
官方写法
conda deactivate；无参数。
通俗解释
提示符上的环境名消失，说明你已退到外面；嵌套激活时按一次退一层。
典型用法
临时回 base 执行管家级操作（升级 conda 本体，见 T3-09）再回来。
注意事项
退出不是删除，房间原样保留；想直接换环境就 activate 新名，不必先 deactivate。
20·T1-08conda list [<包名>]
用途与适用场景
官方定位：列出当前环境已安装的包（名称、版本、build、来源频道）；场景：查账。大白话：翻账本——装了啥、什么版本、哪家超市进的。
官方写法
conda list；可选 conda list <包名> 直接过滤；常用可选项 --revisions（历史账本，见 T4-03）、--export、--json。
通俗解释
打印当前环境的进货明细；带包名时只看那一件的进货记录。
典型用法
确认某包装没装、什么版本：conda list numpy；或过滤 conda list | grep "<关键词>"（Windows 用 findstr）。
注意事项
只看当前环境——执行前先看提示符站对了房间；Channel 列配合 show_channel_urls（T3-03）能查包的来源。
20·T1-09conda install <包名> [<包名2> …] -y
用途与适用场景
官方定位：向当前环境安装包并完成依赖求解；场景：日常上货。大白话：给当前房间添家具，连带全套配件一次搬齐。
官方写法
conda install <包名> [<包名2> …] -y；常用可选项 -y（免确认）、-c <频道>（临时指定源）、=<版本>（见 T2-09）、--file（见 T2-11）。
通俗解释
conda 先算一张"搬家计划表"（要装什么、升降级什么、卸什么），确认后才动手；-y 是直接签字。
典型用法
conda activate demo && conda install numpy pandas -y（见本组示例对照第 ⑨ 条）。
注意事项
先激活目标环境再装（防装错房间）；按 y 前通读计划表的"降级/卸载"区；区间版本要加引号："numpy>=2.1,<3"。
20·T1-10python -m pip install <包名>
用途与适用场景
官方定位（pip 侧）：用当前环境的 pip 从 PyPI 安装包；场景：conda 频道找不到该包时。大白话：conda 没有的小件，上"淘宝"补货。
官方写法
python -m pip install <包名> [==<版本>]；可加 -U 升级、-r <requirements.txt>。
通俗解释
同一个房间的另一条进货渠道；python -m pip 这种写法保证用的是"当前房间的 pip"而不是别处的。
典型用法
conda 里搜不到某个纯 PyPI 小包时：python -m pip install <包名>（见本组示例对照第 ⑩ 条）。
注意事项
永远写 python -m pip 而不是裸 pip（防 PATH 陷阱，pip 可能指向别的环境）；先 conda 后 pip、装过勿回头混装（第 8 章）。

20.3 T2 每周中频：环境生命周期与包进阶

20·T2-01conda create -n <环境名> python=<版本> [<包名> …] -y
用途与适用场景
官方定位：创建一个命名环境，可同时指定 Python 版本与首批包；场景：新任务开工。大白话：开新房间——定门牌、配锅、顺手带首批家具，一次求解到位。
官方写法
conda create -n <环境名> python=<版本> [<包名> …] -y；-n 必填环境名；python=<版本> 可选但强烈建议写；-y 可选。仅 conda create -n <环境名>（不写 python）是官方支持的写法，但会让环境没有明确锅——不推荐（第 5 章）。
通俗解释
建房间时就把锅和家具一次配齐，比"先建空房再一件件搬"少跑一轮依赖求解，也更不容易冲突。
典型用法
conda create -n demo python=3.12 numpy pandas -y（见本组示例对照第 ① 条）。
注意事项
环境名用英文/数字/下划线，无空格无中文；建完 conda activate demo＋python -V 验收；Python 版本写 3.12 这类主次版本即可。
20·T2-02conda create -p <路径> python=<版本> -y
用途与适用场景
官方定位：在指定路径创建环境（前缀式环境）；场景：磁盘分区管理、把环境放进项目目录。大白话：自建别墅——进出都报完整地址。
官方写法
conda create -p <路径> python=<版本> -y；-p 后跟完整路径。
通俗解释
与 -n 建同样的房，只是门牌换成"地址"：之后激活、删除都要用路径。
典型用法
conda create -p /data/envs/demo-path python=3.12 -y（见本组示例对照第 ② 条）。
注意事项
路径建议全英文无空格；设了 envs_dirs（T3-06）后 -n 环境也会默认落大盘，两种方式二选一即可，别混用造成两套管理习惯。
20·T2-03conda create … -c <镜像源地址>
用途与适用场景
官方定位：创建时临时指定一个额外频道；场景：公司镜像/国内镜像只在本次使用。大白话：本次采购只逛指定超市，不改购物偏好卡。
官方写法
conda create -n <环境名> python=<版本> -c <镜像源地址> -y；-c 可重复出现。
通俗解释
-c 只影响这一单，不写进配置；长期用要走 T3-01。
典型用法
conda create -n demo-tmp python=3.12 -c http://mirrors.example.com/conda-forge/ -y（见本组示例对照第 ③ 条）。
注意事项
仅本次生效；镜像地址会随镜像站迁移而变（待核实 性质，用前核对镜像站帮助页）。
20·T2-04conda env remove -n <环境名> -y
用途与适用场景
官方定位：删除整个环境（两种等价写法）；场景：结项清理、废环境回收。大白话：拆房间——东西全没，不可逆。
官方写法
conda env remove -n <环境名> -y，或 conda remove -n <环境名> --all -y；路径式换 -p <路径>。
通俗解释
两条命令效果一样：整间房连锅带家具全拆。删除前先拍快照留底（T2-07）。
典型用法
conda env remove -n demo-old -y（见本组示例对照第 ⑭ 条）。
注意事项
删前 conda env list 对准名字；正在激活的环境删不掉，先 deactivate；删后清理 IDE/笔记本内核里的残留选项。
20·T2-05conda rename -n <旧名> <新名>
用途与适用场景
官方定位：重命名环境 conda ≥4.14；场景：命名规范统一后批量改门牌。大白话：换门牌，屋里东西一件不动。
官方写法
conda rename -n <旧名> <新名>；路径式用 -p <路径>。
通俗解释
老版本 conda 没这条：当时用"克隆＋删除"两步等效；新版本一条命令完成。
典型用法
conda rename -n demo-tmp demo-old（见本组示例对照第 ⑤ 条）。
注意事项
改名后要同步更新 IDE、笔记本内核、启动脚本里对旧环境名的引用——门牌换了，导航没换就会"找不到房"。
20·T2-06conda create … --clone <旧环境>
用途与适用场景
官方定位：克隆已有环境；场景：做实验副本、升级前备份。大白话：复制一间平行房间——硬链接复用缓存，几乎不占新盘。
官方写法
conda create -n <新名> --clone <旧名> -y；或 conda create -p <路径> --clone <旧名>；可选项 --copy（改为真拷贝）。
通俗解释
新房间与旧房间此刻一模一样，之后互不影响——大胆在新房里试升级，坏了回旧房。
典型用法
conda create -n demo-bak --clone demo -y（见本组示例对照第 ④ 条）。
注意事项
网络盘/NFS 上建议加 --copy（硬链接跨盘无效）；原文的 --exclude 排除包选项未见于官方文档 → 见 20.6。
20·T2-07conda env export … > <文件.yml>
用途与适用场景
官方定位：把环境导出为 YAML 文件；场景：留底、交接、跨机复现。大白话：拍快照存菜谱，别人照方抓药。
官方写法
conda env export [-n <环境名>] > <文件.yml>；可选项 --from-history（只含你点名装过的包）、--no-builds（跨平台更稳）。
通俗解释
默认导出"连赠品都写全"的完整菜谱；--from-history 是精简版菜谱——只写你点过名的菜，依赖让 conda 现场再配。
典型用法
conda env export -n demo > demo-environment.yml（见本组示例对照第 ⑥ 条）。
注意事项
yml 顶部的 channels 小节不能删——它是复现的关键；精简菜谱换平台时依赖可能装不上，要留完整版备用。
20·T2-08conda env create -f <文件.yml>
用途与适用场景
官方定位：按 yml 文件重建环境；场景：换机、接手同事项目。大白话：照菜谱异地重建一间同样的房。
官方写法
conda env create -f <文件.yml> [-n <新名>]；-f 必填文件路径；-n 用于覆盖 yml 里的环境名。
通俗解释
conda 按 yml 逐条抓货；yml 里有 pip: 小节时它会自动调用 pip 装那部分。
典型用法
conda env create -f demo-environment.yml -n demo-restore（见本组示例对照第 ⑦ 条）。
注意事项
与已有环境重名时用 -n 改名；下载慢可临时加 -c 指定镜像。
20·T2-09conda install <包名>=<版本>
用途与适用场景
官方定位：安装指定版本的包；场景：复现论文环境、锁关键依赖。大白话：点名要某年某月的那批货。
官方写法
conda install <包名>=<版本> [<其他包> …] -y；=3.9 这类两位版本是模糊匹配（主次版本），=1.26.0 三位是精准锁定。
通俗解释
版本号前用 = 而不是 pip 的 ==；多包空格分隔，一次求解防止"装了新包、拆了旧包"。
典型用法
conda install numpy=2.1 -y；GPU 组合把 tensorflow 与对应 cudatoolkit 包写在同一单里（见本组示例对照第 ⑧ 条）。
注意事项
版本号是否存在以 conda search（T2-14）结果为准，别凭记忆写；区间写法加引号 "numpy>=2.1,<3"。
20·T2-10conda install <本地包文件>
用途与适用场景
官方定位：直接安装本地 conda 包文件；场景：内网传包、离线环境。大白话：不上网，直接装手上这箱货。
官方写法
conda install </本地路径/包文件.conda> -y；支持 .conda 与 .tar.bz2 两种包文件格式。
通俗解释
把别人拷给你的包文件直接交给 conda 安装；它仍会做依赖检查。
典型用法
conda install /data/pkgs/somepkg-1.0.conda -y（虚构文件名，见本组示例对照第 ⑨ 条）。
注意事项
路径含空格要加引号；Windows 下注意盘符写法与正斜杠。
20·T2-11conda install --file <requirements.txt>
用途与适用场景
官方定位：按清单文件批量安装；场景：一次买齐一整个项目的依赖。大白话：拿购物单一次采购到位。
官方写法
conda install --file <requirements.txt> -y；清单每行一条 spec（包名 或 包名=版本）；conda create -n <名> --file <清单> 同理。
通俗解释
清单是纯文本，一行一个包；conda 把整张单子一次求解。
典型用法
conda install --file requirements.txt -y（见本组示例对照第 ⑩ 条）。
注意事项
相对路径按当前 shell 目录解析，建议写绝对路径；清单里不要混 pip 专属语法（如 git+ 开头行）。
20·T2-12conda remove <包名>
用途与适用场景
官方定位：从当前环境卸载包；场景：清掉误装、减重。大白话：退货——默认连带退掉只为它装的孤儿依赖。
官方写法
conda remove <包名> -y；变体 --force（跳过依赖检查蛮力退）、--no-deps（只退主件不退连带）。
通俗解释
普通退货会把"没人再需要的赠品"一起退；--force 是不管账本硬退，可能留下断链。
典型用法
conda remove matplotlib -y（见本组示例对照第 ⑪ 条）。
注意事项
卸前先 conda search <包名> --info 看清谁依赖它；--force 只在排障时用，用后建议跑一次 conda doctor（T4-02）。
20·T2-13conda update <包名>
用途与适用场景
官方定位：升级环境内已安装的包；场景：追新版本、修已修复的 bug。大白话：换新款。
官方写法
conda update <包名> -y；或 conda update <包名>=<目标版本> -y（升到指定高版本而非最新）；--all 升整间房。
通俗解释
和 install 一样先出计划表再动手；升级引发的连锁降级会明示在表里。
典型用法
conda update pandas -y（见本组示例对照第 ⑫ 条）。
注意事项
升级前先 conda env export 留底；计划表的降级区必看（第 6 章）；--all 在业务环境慎用。
20·T2-14conda search <包名>
用途与适用场景
官方定位：在配置的频道中检索包及可用版本；场景：装之前先侦察。大白话：货架侦察——有没有货、有哪些年份的货。
官方写法
conda search <包名>；变体 conda search <包名>=<版本>、conda search "*<关键词>*"；可选项 --info（看依赖与许可证）、-c <源>（限定频道）。
通俗解释
搜索结果按频道列出各版本；带 --info 相当于看商品详情页。
典型用法
conda search "numpy>=2.1"（见本组示例对照第 ⑬ 条）。
注意事项
找不到不等于不存在——换频道再试、核对包名拼写（第 6 章）；镜像频道滞后于官方源属正常。

# ===== T2 环境生命周期：建→改→传→拆 =====
conda create -n demo python=3.12 numpy pandas -y          # ① 建房+配锅+首批家具（一次求解）
conda create -p /data/envs/demo-path python=3.12 -y       # ② 路径式环境（落大盘）

20.4 T3 每月/季度：配置、治理与批量

20·T3-01conda config --add channels <镜像源地址>
用途与适用场景
官方定位：向配置添加频道（头部插入）；场景：配国内/公司镜像提速。大白话：把一家超市提到最优先——这是镜像加速的核心一步。
官方写法
conda config --add channels <镜像源地址>；写进 .condarc 的 channels 列表（头插=优先级升高）。
通俗解释
此后所有安装/搜索默认先逛这家；列表顺序就是优先顺序（配合 T3-04 的 strict）。
典型用法
conda config --add channels http://mirrors.example.com/conda-forge/（见本组示例对照第 ① 条）。
注意事项
镜像地址会随镜像站迁移而变（待核实 性质，以镜像站帮助页为准）；同一源勿重复添加；改完用 conda config --show channels 验收顺序。
20·T3-02conda config --remove channels <镜像源地址>
用途与适用场景
官方定位：移除指定频道，或整键清空；场景：镜像失效回退、配置重置。大白话：踢掉失效超市；--remove-key channels 是整张购物卡重置。
官方写法
conda config --remove channels <镜像源地址>；整列清空：conda config --remove-key channels。
通俗解释
remove 精准踢一家（地址要一字不差）；remove-key 把频道列表整个删掉，恢复默认。
典型用法
镜像站迁移后旧地址失效：先 remove 旧地址再加新地址（见本组示例对照第 ② 条）。
注意事项
remove 的地址必须与配置里的写法完全一致（含末尾斜杠与否）；remove-key 后国内镜像全没了，需按 T3-01 重新配置。
20·T3-03conda config --set show_channel_urls true
用途与适用场景
官方定位：让 conda list 等输出显示包的来源频道；场景：排查包的进货来源。大白话：账本里每件货都标明哪家超市进的。
官方写法
conda config --set show_channel_urls true；取值 true/false。
通俗解释
打开后 conda list 的 Channel 列直接可见，回答"这个包到底从哪来的"。
典型用法
排查依赖混乱时先开它再看账本（见本组示例对照第 ③ 条）。
注意事项
只影响显示，不影响安装行为；排障完成后保留即可。
20·T3-04conda config --set channel_priority strict
用途与适用场景
官方定位：设置频道优先级模式为严格；场景：多频道混用防串味。大白话：严格按超市排序进货——低优先源的更新版本不许盖过高优先源。
官方写法
conda config --set channel_priority strict；可选值 strict/flexible/disabled。
通俗解释
strict 是官方推荐：依赖求解只在最高优先频道能凑齐时才用下一层，防"老版压新版"的隐性冲突（第 7 章）。
典型用法
配镜像的同时锁死求解纪律（见本组示例对照第 ④ 条）。
注意事项
与 flexible 的行为差异详见 7.2；换模式后老环境不受影响，只影响之后的求解。
20·T3-05conda config --set auto_activate_base false
用途与适用场景
官方定位：禁止终端启动时自动激活 base；场景：保持终端"干净"。大白话：开终端不再自动站进管家房——防手滑把包装进 base。
官方写法
conda config --set auto_activate_base false；取值 true/false。
通俗解释
关掉后新终端提示符没有 (base)；要用再手动 activate。
典型用法
新机一次性配置（见本组示例对照第 ⑤ 条）。
注意事项
想恢复改回 true；关掉后注意别在无环境状态下裸跑 conda install——那会装进 base。
20·T3-06conda config --set envs_dirs <路径>
用途与适用场景
官方定位：设置环境默认存放目录；场景：系统盘小、环境建到大盘。大白话：新房默认盖到大盘上。
官方写法
conda config --set envs_dirs <路径>；多路径用 --add envs_dirs <路径> 逐个头插；移除用 --remove envs_dirs <路径>。
通俗解释
以后 conda create -n 的新环境都落在这里，不再挤系统盘。
典型用法
conda config --set envs_dirs /data/envs（见本组示例对照第 ⑥ 条）。
注意事项
路径须可写；与 pkgs_dirs（T3-07）同一块盘时硬链接才生效省盘（第 15 章）；改后 --show 验收。
20·T3-07conda config --set pkgs_dirs <路径>
用途与适用场景
官方定位：设置包缓存目录；场景：缓存占盘大户迁往大盘。大白话：驿站迁大盘——所有下载的货先堆这里。
官方写法
conda config --set pkgs_dirs <路径>；多路径用 --add pkgs_dirs <路径>。
通俗解释
环境安装时从驿站硬链接进货，同版本包只存一份。
典型用法
conda config --set pkgs_dirs /data/conda_pkgs（见本组示例对照第 ⑦ 条）。
注意事项
与 envs_dirs 同盘（第 15 章）；迁移后旧缓存不自动搬家，老环境仍指向原目录。
20·T3-08conda clean -p|-t|-i|-a
用途与适用场景
官方定位：清理包缓存；场景：磁盘告急、季度例行。大白话：扫驿站——清死包/压缩包/索引缓存。
官方写法
conda clean -p（无环境引用的死包）、-t（tar 压缩包）、-i（索引缓存）、-a（全部）；可选项 -y（免确认）、-d（预演不删）。
通俗解释
-p 腾最多盘；-t 清下载原件；-i 清搜索目录缓存，清完下次联网慢一次。
典型用法
先 conda clean -p -d 预演看数量，确认后再 conda clean -p -y（见本组示例对照第 ⑧ 条）。
注意事项
只动缓存不动环境；建议每月一次；-a 之后离线安装（T4-05）需要重新预下载。
20·T3-09conda update conda -y
用途与适用场景
官方定位：升级 conda 自身（或整套 Anaconda 发行版）；场景：月度保养。大白话：管家保养；conda update anaconda 是全家桶整套升级。
官方写法
conda update conda -y；conda update anaconda -y（仅 Anaconda 发行版）；conda 26.5+ 推荐 conda self-update。
通俗解释
在 base 里给管家换新工服；全家桶升级动静大，业务环境别跑。
典型用法
回 base（conda deactivate 到底）再执行（见本组示例对照第 ⑨ 条）。
注意事项
必须在 base 执行；原文提到的 --force 升级写法未见官方文档 → 见 20.6。
20·T3-10conda run -n <环境名> <命令>
用途与适用场景
官方定位：不激活环境直接在其中执行命令；场景：脚本、CI、一行式验收。大白话：不进房间借手办事。
官方写法
conda run -n <环境名> <命令>；多条用 conda run -n <环境名> bash -c "<命令1>; <命令2>"（Windows 换 cmd /c）。
通俗解释
conda 替你临时进房办完事就退，提示符全程不动。
典型用法
验解释器：conda run -n demo python -c "import sys; print(sys.executable)"（见本组示例对照第 ⑩ 条）。
注意事项
长任务前先这样验一次 sys.executable 防跑错环境；输出可能缓冲到结束才一起吐，属正常不是卡死。
20·T3-11conda config --show-sources / --show / --reset
用途与适用场景
官方定位：查看配置来源/全量配置/恢复默认；场景：配置排障。大白话：看配置来自哪几份文件／全量看一遍／一键恢复出厂。

通俗解释

20·T3-12批量导出/导入/更新/清理（循环脚本）
用途与适用场景
官方定位：shell 循环批量调用上述官方命令；场景：换机迁移、季度大盘点。大白话：遍历所有房间逐个拍快照/重建/升级/打扫。

通俗解释

20.6 存疑命令对照：原文有、但未见于官方文档（勿直接抄）

为什么要这一节

外部文档声称"已全面覆盖无遗漏"，但其中若干条命令在 conda 官方命令清单（conda commands / docs.conda.io，26.x）中无出处，疑似 AI 生成内容或与第三方工具混淆。本章不把它们混入主卡片，而是逐条列出并给出官方/成熟替代——这样新人既不会被假命令卡住，也能看懂"为什么网上抄来的命令跑不通"。

1. conda lock <包名> / conda unlock — 核实结论：官方命令清单无此子命令。替代：锁版本用 spec 写法 包名=版本；跨机精确锁定用社区工具 conda-lock（带连字符，第 13 章）；防误升级用 conda list --revisions 账本。

2. conda env verify [-n <环境>] [--fix] — 核实结论：无此子命令。替代：体检用 conda doctor（T4-02）；修复靠重装受损包或 --revision 回滚（T4-03）。

3. conda env freeze / unfreeze — 核实结论：无此子命令。替代："只读保护"靠纪律+conda-lock 锁文件；生产环境治理见第 17 章五支柱。

4. conda history [rollback N] — 核实结论：无此子命令。替代：conda list --revisions 查历史；conda install --revision=<N> 回滚。

5. conda check -n <环境> — 核实结论：无此子命令。替代：依赖冲突排查：conda search <包> --info 看依赖 + conda doctor。

6. conda info <包名> --dependencies — 核实结论：无此用法（conda info 不接包名）。替代：conda search <包名> --info，输出含 dependencies 字段（第 19 章 T2-11）。

7. conda tree list -n … — 核实结论：名字写错，官方无此命令。替代：第三方工具 conda-tree（T4-09，先 conda install -c conda-forge conda-tree）。

8. conda install <包> --download-only -d <路径> — 核实结论：参数拼接有误。替代：-d 实为 --dry-run（预演）；预下载用 conda create -n <名> --download-only …（T4-04），缓存路径由 pkgs_dirs 配置（第 14 章）。

10. conda deactivate --all — 核实结论：未见官方文档 待核实。替代：连按几次 conda deactivate 直至退到底（第 5 章 5.5）。

11. conda list --short / --conda / --pip / --channel — 核实结论：未见官方文档 待核实。替代：官方确认的过滤/导出类选项：--revisions、--explicit、--md5、--export、--json、--from-history；来源过滤看 Channel 列+show_channel_urls（T3-03）。

12. conda update <包> --force / conda install … --force-reinstall — 核实结论：未见官方文档 待核实（--force 确认存在于 remove）。替代：修复坏包用 remove 后重装，或 --revision 回滚。

13. conda env remove --force / conda remove --file — 核实结论：未见官方文档 待核实。替代：环境删不掉时检查占用/权限（先 deactivate）；批量卸载逐包执行或写循环脚本。

14. conda env export --channel <源> / conda create --clone … --exclude — 核实结论：未见官方文档 待核实。替代：导出后手动编辑 yml 的 channels 小节；克隆排除包：先克隆再用 remove 卸掉不想要的包。

15. conda install <包> --retries <次数> — 核实结论：未见官方文档 待核实。替代：重试/超时策略在 .condarc 配置（如 remote 系列键），用 conda config --describe 查可用键名。

20.7 一次性配置 vs 每个项目配置（本章版）

一次性配置指装机或入职接入环境时做一次、写进用户级 .condarc、对所有项目共享的设置——换项目不用重做，只在换电脑/重装时重来：

  • conda init <shell>：让终端认识 conda；<shell> 替换为 bash/zsh/cmd.exe/powershell；改后重开终端验证。
  • 镜像频道列表与 show_channel_urls true：固定进货超市、账本标来源；镜像地址随镜像站迁移会变（待核实），以镜像站帮助页为准。
  • channel_priority: strict：锁死分层求解纪律；值固定，无需替换。
  • auto_activate_base: false：开终端不自动进 base；值固定 true/false。
  • envs_dirs / pkgs_dirs：房间与驿站迁大盘；替换为本机可写大盘路径；两目录同一块盘硬链接才生效。
  • ssl_verify、remote_*_timeout_secs：内网证书与网络耐性；替换为证书路径/秒数，按网络环境调整。

每项目配置指跟随具体环境或代码仓库走的设置——环境删除即消失，或随 yml 文件在机器间"旅行"：

  • conda create -n <项目环境> python=<版本>：立项开房；环境名建议带项目前缀（如 yf-），版本以项目需求为准；建后 activate 验收。
  • conda install <包>=<版本>：依赖定型；版本号以 search 结果为准。
  • conda env export > <文件.yml>：菜谱入仓库；导出后检查 channels 小节是否完整。
  • export CUDA_VISIBLE_DEVICES=<卡号>：项目训练用卡声明（shell/运行时层，不写 .condarc）；卡号按 nvidia-smi 实际情况替换。
  • conda install --revision=<N>：项目环境回滚依据；N 抄自 revisions 输出。
  • conda env remove -n <项目环境>：结项拆房；删前 export 留底、env list 对名。

Q1：Anaconda 和 Miniconda 到底装哪个？

要开箱即用的全家桶（教学/演示/大硬盘）→ Anaconda；自用主力机/公司服务器 → Miniconda；有许可顾虑或想纯社区频道 → Miniforge。三者用起来 95% 命令相同。

Q2：conda、Anaconda、conda-forge 是一家公司吗？

不是。conda 是开源项目（社区治理）；Anaconda 是公司与其发行版；conda-forge 是社区频道。defaults 频道归 Anaconda 公司条款管辖，conda-forge 与 conda 本体不归。

Q3：为什么 conda 装的 numpy 比官网还旧？

频道优先级（strict 下高优先级频道说了算）+ 你的 spec 是裸名。收紧版本或调频道顺序，见第 7 章 7.2。

Q4：pip 装的东西 conda list 里能看到吗？

能看到（标 pypi 来源）但不进 conda 账本——求解器不感知它们，这是混用纪律存在的根本原因（第 8 章）。

Q5：环境能直接复制文件夹迁移吗？

不能。绝对路径+硬链接结构会被破坏。正道：yml 重建 / conda-pack / conda rename（同机改名）。

Q6：误删环境能恢复吗？

环境本身不能；但包缓存还在（clean 前），重建同名环境基本秒装。所以“删前 export 留底”值得养成习惯。

Q7：公司 300 人，没买许可证，还能用吗？

conda 本体与 conda-forge 随便用；defaults 频道需切换掉（全员 Miniforge 最省心）。详见 17.3。

Q8：Jupyter 里装的包 import 不到怎么办？

三步：确认右上角内核是目标环境 → sys.executable 验明 → 重启内核（已加载模块不会热更新）。

Q9：conda clean -a 会不会删我的环境？

不会，只清缓存（未被链接的包、索引、日志）。放心执行；环境在 envs/ 原地不动。

Q10：怎么把环境冻结不再变化？

不跑 update --all、spec 全带版本号、用 conda-lock 固化归档即可。个别版本曾提供锁步类开关（名称随版本变动，以 conda update --help 为准，待核实）。
